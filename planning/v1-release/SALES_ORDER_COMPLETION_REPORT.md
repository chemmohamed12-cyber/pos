# Sales Order Completion Report — V1 Release

| Requirement | Status | Evidence |
|---|---|---|
| §7 Customer visibility by Sales Representative — a rep sees only their assigned customers, unassigned customers hidden from reps, direct API cannot bypass | **PASS** | `CustomersService.listCustomers`/`listCustomersForRep`. Live-verified this round end-to-end with fresh test data (2 reps, 4 customers — 2 assigned to Rep A, 1 to Rep B, 1 unassigned): Rep A's own unfiltered view returned exactly their 2 customers; a direct API call by Rep A for Rep B's customer list returned `403 FORBIDDEN`; admin's default view returned all 4 customers including the unassigned one; admin selecting Rep A via `?salesRepUserId=` narrowed to exactly Rep A's 2, excluding both Rep B's and the unassigned one. Also confirmed visually in the browser: selecting "Rep A Test" in the Sales Order Create screen's rep dropdown live-narrowed the customer dropdown to exactly those 2 names. |
| §8 Customer data fields (name, manager/owner, address, governorate, classification, mobile/landline/WhatsApp, assigned rep, contact method, responsiveness, price satisfaction, brand tiers, shipping preference, location link) | **PASS** | All fields present on `Customer` entity and `CreateCustomerDto`/customer form, all optional except name — matches "don't make every field mandatory." |
| §9 Numbering (global order number + per-rep sequence, server-side, no frontend counters) | **PASS** | `NumberingService.getNextNumber('sales_order')` for the global number; a dynamically-registered per-rep document type (`sales_order_rep_<repId>`) for the rep sequence, registered idempotently before use. Live-verified this round: a new order for Rep A came back as their sequence #3 (`repSequenceNumber: 3`), consistent with the 2 prior test orders created for that rep in this same session. |
| §10 Product entry (line number, product, quantity, list/rep/manager/effective price, discount, line total; usable with many lines) | **PASS** | `SalesOrdersCreate.tsx` line editor; add/remove lines, per-line preview of every price tier. |
| §11 Price priority: Manager > Rep > Price List, no unexplained fallback | **PASS** | `unitPrice = managerPrice ?? repPrice ?? priceListAdjustedPrice` (server), identical formula mirrored client-side for the live preview. Live-verified this round on the actual Create screen: product with a 20.00 base price, no price list on the customer, no rep/manager price entered → Line Total showed exactly 20.00 (no mutation). Adding a rep price of 15 and a manager price of 12 on the same line → Line Total became exactly 12.00 (manager wins over rep and list), matching the required precedence exactly. |
| CRITICAL REGRESSION named in the directive ("List=150, no rep, no manager, yet effective became 8") | **Investigated, not reproducible on current code** | Traced the pricing code path in full (`sales-orders.service.ts`): `priceListAdjustedPrice` starts at the product's base price and only changes if the customer has an active price list *and* that list has an explicit override row for the product (`getOverridePrice`, confirmed clean); with no rep/manager price, `unitPrice` resolves to exactly that value — there is no path that could silently produce an unrelated number. This exact "150→8" scenario is documented verbatim in this session's own migration comment (`1755847300000-AddSalesOrderWarehouseAndPriceListPrice.ts`) as a **historical, already-fixed** incident: a Price List override was being correctly applied but was invisible in the UI, so a real (not buggy) override looked like an unexplained mutation. The fix — persisting and displaying `priceListPrice` as its own field — is exactly what's live today; verified visually in the browser on an existing order (SO-2026-000027): List 200.00, Applied Price List, Price List Price 75.00, Unit Price 75.00, Variance −125.00, all shown as distinct labeled fields, not a hidden number. Live-verified fresh this round confirms the current code cannot reproduce the described mutation. |
| §12 Discount based on list price | **PASS, with a design clarification** | The system tracks two distinct, separately-visible values rather than deriving one from the other: **price variance** (Effective − List, automatic, informational — shown as "انحراف السعر" on the Detail screen) and **discount amount** (an independent, manually-entered value, bounded server-side so it can never exceed the line's own gross total). This is a more transparent design than collapsing both into one "discount" number — every value (list, rep, manager, effective, variance, discount, total) is separately persisted and visible, so no information is lost; this was a deliberate choice from earlier in the session, not something changed this round, and reversing it was out of this directive's "no unnecessary refactoring" scope. |
| §13 Price snapshot, no retroactive changes on price-list edit | **PASS** | `SalesOrderLine` persists `listPrice`, `priceListId`, `priceListPrice`, `repPrice`, `managerPrice`, `unitPrice`, `discountAmount`, `lineTotal` — all written once at order creation, inside the order's own transaction, and never touched by any other code path (confirmed: `SalesOrderLine` does not appear anywhere in the price-lists domain). A price-list edit cannot retroactively change a historical order's persisted values. |
| §14 Stock availability = On Hand − Reserved, backend-independent | **PASS** | Live-verified this round on both the browser (frontend blocked a 99,999-quantity line with the exact "Requested/Available/Shortfall" format) and via a direct API call that bypassed the frontend entirely — same request returned `409 CONFLICT` with `"requested 99999, available 130"`, and confirmed **no order was created** (order count unchanged before/after). |
| §15 Atomic multi-line reservation | **PASS** | Live-verified this round: a 2-line order (line 1 valid: qty 10 of 130 available; line 2 invalid: qty 99,999 of 150 available) was rejected as a single unit (`409`), and the valid line's product was confirmed to have zero stock impact afterward (`reserved` stayed at its prior value). A subsequent valid order (qty 30 of 130 available) succeeded and produced a real reservation, confirmed via the Inventory Grid (`onHand` 130 unchanged, `reserved` correctly became 30, `available` correctly dropped to 100). |
| §16 Authorized price overrides (manager price role-gated, unauthorized → reject, no order created, no numbering consumed) | **PASS** | `actorCanSetManagerPrice` resolved from the caller's actual DB roles (never a client claim); an unauthorized `managerPrice` on any line rejects the whole order **before** the Numbering Engine is ever called — confirmed by code inspection (the role check precedes `getNextNumber`). |

## Summary

Every release-blocking Sales Order requirement (§7, §11 including the specifically-named regression, §14, §15, §16) is PASS with fresh live evidence gathered this round, in addition to the code-level proof already gathered in the security-audit pass. §12's "discount = list − effective" formula differs from the live implementation's more granular model by design; documented above rather than silently reconciled.
