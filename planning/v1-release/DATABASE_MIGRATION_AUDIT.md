# Database & Migration Audit — Final (V1 Release)

Date: 2026-08-23. Scope: 70 migrations in `backend/src/database/migrations/*.ts`, cross-checked against 12 entity files. Read-only research pass (agent, 70 tool uses), then independently spot-verified.

## Findings

| # | Check | Result |
|---|---|---|
| 1 | Migration ordering/uniqueness | **Medium** — 9 pairs of migrations share a timestamp (18 of 70 files). TypeORM's `MigrationExecutor` sorts by timestamp with a stable sort and only rejects duplicate *class names*, not duplicate timestamps, so `migration:run` does not fail. Every colliding pair was manually checked for a real dependency (one altering a table the other creates) — none exists, and every colliding terminology seed uses `ON CONFLICT (code) DO UPDATE`. **Not a functional blocker**, but a genuine hygiene gap — a landmine for the next migration inserted between these timestamps. Non-blocking, recommended cleanup. |
| 2 | Migration naming convention | Clean — all 70 `name = 'ClassName<timestamp>'` properties exactly match their exported class and filename prefix. |
| 3 | Entity ↔ migration column consistency | Clean — every entity column has a matching migration (sampled: `Warehouse`, `WarehouseTransaction`, `WarehouseTransactionLine`, `StockMovement`, `Product`, `Customer`, `SalesOrder`, `SalesOrderLine`, `PriceList`, `PriceListItem`, `BillOfMaterial`, `BomComponent`), and no migration adds a column with no entity field. |
| 4 | Foreign-key constraints | **Medium** — migrations through `1755846200000-CreateIntegrationTables.ts` consistently declare `REFERENCES` constraints; starting at `1755846600000-CreateWarehouseTransactionTables.ts` (the Warehouse ERP Phase-1 / final Sales-Order-directive work), several UUID columns (`warehouseId`, `destinationWarehouseId`, `createdByUserId`, `approvedByUserId`, `postedByUserId` on warehouse transactions; `responsibleUserId` on warehouses; `warehouseId`, `createdByUserId` on sales orders) are declared as bare `UUID` with no FK. This matches the entity declarations exactly (plain `@Column({type:'uuid'})`, no `@ManyToOne`), so it is a consistent design choice, not an entity/migration mismatch — but it is a real loss of the referential-integrity discipline the rest of the schema follows. Every one of these IDs is validated by the service layer before being written (e.g. `getWarehouse` 404s on an unknown id, product/customer lookups 404 before use), so there is no live data-integrity gap today — this is a hardening recommendation, not a blocker. |
| 5 | Uniqueness / indexes | Clean — all uniqueness-critical columns are unique-indexed (`products.sku`, `warehouses.code`, `customers.code`, `price_lists.code`, `sales_orders.orderNumber`, `warehouse_transactions.transactionNumber`, `bill_of_materials.finishedProductId`, plus the compound uniques on price-list items and BOM components). High-volume join columns are indexed (`stock_movements(warehouseId,productId)`, `stock_reservations(warehouseId,productId)` + `salesOrderId`, `sales_order_lines.salesOrderId`, `warehouse_transactions.warehouseId`). Low/Note: `warehouse_transaction_lines.productId` and `sales_order_lines.productId` aren't indexed, matching the entity's own design — worth revisiting for reporting-query performance, not a release blocker. |
| 6 | Nullability/defaults on `ALTER` | Clean — all 5 `ADD COLUMN ... NOT NULL` statements carry a `DEFAULT`; both `SET NOT NULL` migrations correctly follow nullable-add → backfill `UPDATE` → `SET NOT NULL`. No migration would fail against a populated table. |
| 7 | Down migrations | Clean — spot-checked 30+ migrations spanning the full timeline; every `down()` is present, non-empty, and correctly reverses `up()` in the right order (child rows before parent tables, numbering-sequence rows cleaned up). |
| 8 | Dev-only / hardcoded demo data | Clean — no hardcoded emails, literal UUIDs, or demo/fake/sample data in any migration. The only `'admin'` literal is legitimate role-key seeding, consistent with the documented first-user-becomes-admin bootstrap flow. |
| 9 | `numbering_sequences` seeds vs. code usage | Clean — all 8 seeded document types (`sales_order`, `customer`, `sales_rep`, `shipment`, `price_list`, `assembly`, 5 warehouse-transaction types) match every `getNextNumber(...)` call site. The one dynamic key (`sales_order_rep_<userId>`) self-registers idempotently before use, correctly needing no seed row. |

## Live verification this round

- `npm run migration:run` against the project's real dev Postgres (port 5432, database `daii_dev`, matching `.env`): **all 70 migrations applied, "No migrations are pending."**
- **Environment incident, resolved, not a migration defect**: mid-session, this Postgres became unreachable (`ECONNREFUSED`). Root cause: this project's dev Postgres is a portable, no-installer install (per `LOCAL_DEVELOPMENT.md`) that had been running from inside a *different, concurrently-active Claude Code session's own temp scratchpad directory* — not a Docker container, not a Windows service. That process was killed abruptly (not via `pg_ctl stop`), which is exactly why it disappeared with no trace. It was located, confirmed dead (its stale `postmaster.pid` referenced a PID that no longer existed), and restarted in place via `pg_ctl start` against its original data directory — Postgres performed its own standard automatic WAL crash-recovery on startup (a normal, non-destructive operation: "database system was not properly shut down; automatic recovery in progress" → "database system is ready to accept connections"). No data was lost; the full original dataset (22 sales orders, all original customers, all warehouse/product test fixtures from earlier in this session) was confirmed present immediately after. A separate, unrelated native Windows PostgreSQL 18 service was also found running on port 5433 during the outage — this belongs to a different, much smaller dataset with no connection to this project and was left untouched.

## Summary

No Blocker- or High-severity issues found. The two Medium findings (duplicate migration timestamps, FK discipline dropped in the newest migrations) are real but non-blocking — neither breaks `migration:run` against a populated database nor causes a runtime column-not-found or orphaned-row error today. Recommended as fast follow-ups, not release blockers.
