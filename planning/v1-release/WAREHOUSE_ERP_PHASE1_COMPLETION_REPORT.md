# Warehouse ERP Phase 1 — Completion Report

Scope: the Inventory/Warehouse domain, rebuilt per the CTO's "Warehouse & Inventory V1 / Phase 1 Integration" directive earlier this session and confirmed in scope by the "FINAL EXECUTION DIRECTIVE" — explicitly **not** Purchasing, Production, or full GL/AP-AR (out of scope per documented Non-Goals / ADR-007, and re-confirmed by the CTO this session after a scope-conflict escalation).

| Requirement | Status | Evidence |
|---|---|---|
| 2.1 Warehouse Master (code, name, location, responsible user, active/inactive, audited) | **PASS** | `Warehouse` entity has `location`, `responsibleUserId`, `status`; `InventoryService.setWarehouseStatus` validates the transition and audits it; `assertWarehouseActive` blocks new transactions against an inactive warehouse (checked in both `createTransaction` and `startCount`). Frontend `Warehouses.tsx`: location/responsible-user inputs, admin-only Activate/Deactivate toggle. |
| 2.2 Inventory Grid (server-side search/sort/pagination, On Hand/Reserved/Available/Status/Last Movement, zero-stock rows, Excel export) | **PASS** | `InventoryService.getWarehouseInventoryPage` — paginated/searched/sorted SQL query with a `LEFT JOIN` from `products` so zero-stock products appear as explicit rows. `Inventory.tsx` rewritten around it: warehouse selector, 300ms-debounced search, sortable columns, `PAGE_SIZE=50` pagination, Excel export link. Live-verified this round: grid correctly showed live `onHand`/`reserved`/`available` for test products after each transaction. |
| 2.3 Movements as real documents (system number, paper reference, warehouse, lines, user, date/time, reason, reference, status, audit) | **PASS** | `WarehouseTransaction`/`WarehouseTransactionLine` entities; `NumberingService` generates `WH-IN/OUT/TR/ADJ/CNT-YYYY-NNNNNN` server-side (never frontend-generated); `movementDate` field distinct from immutable `createdAt`; every transition audited via `AuditService`. |
| 2.4 Multi-line documents | **PASS** | `WarehouseTransactionForm.tsx` supports add/remove lines, per-line product search and validation; `createTransaction` accepts an array of lines in one call. |
| 2.5 Stock validation (Available = On Hand − Reserved, server-side, Requested/Available/Shortfall) | **PASS** | `requiredCheckQuantity` + `getAvailableInTransaction` in `postTransaction`; live-verified this round: an Issue transaction requesting 99,999 against 150 available was rejected with `"Insufficient stock ... requested 99999, available 150, short by 99849"`. |
| 2.6 Whole-document atomicity | **PASS** | `postTransaction` validates every line's requirement *before* writing any movement, inside one `dataSource.transaction`, under sorted per-(warehouse,product) advisory locks. Live-verified this round: a 2-line Issue (line 1 valid, line 2 requesting 99,999 against 150 available) was rejected as one unit — line 1's product stock was confirmed unchanged afterward (`onHand` stayed 130, not partially reduced), and the transaction correctly stayed at `approved` state (not fake-`posted`) so it can be retried. |
| 2.7 Concurrent operations (deterministic lock ordering) | **PASS** | `[...pairs].sort()` before acquiring `pg_advisory_xact_lock` per pair — same pattern in `InventoryService.reserveStock`/`assembleProduct`. Covered by dedicated unit tests asserting sorted-lock-ordering; not re-run live this round (no practical way to force real concurrent requests through this session's tooling), so this line item rests on the unit-test proof, not a fresh live race test. |
| 2.8 Approval / Process Engine, default-deny for internal actions | **PASS** | Draft→Submitted→Approved→Posted→Reversed preserved via `WAREHOUSE_TRANSACTION_PROCESS`; the `auto_post` internal-only action bypass found in this round's security audit is fixed — default-deny confirmed live (rejected for both a regular user and admin). |
| 2.9 Reversal (never delete, full audit trail) | **PASS** | `reverseTransaction` creates a new transaction of the same type with every line negated, linked via `reversalOfTransactionId`, posts immediately; original transaction's Process Engine history untouched. Verified via unit tests this session; not re-exercised live this round (lower risk — no code path changed here since it was last live-verified). |
| 2.10 Stock Count (system vs. physical quantity, variance, audit) | **PASS** | `startCount` seeds lines with `systemQuantity`, `submit` requires every line to have a `physicalQuantity` recorded, the resulting `quantity` (variance) drives an `adjustment`-type movement on post. Built and unit-tested this session; not re-exercised live this round. |
| §3 Financial control (who/when/where/what/how much/why/reference/approved-by/posted-by, no silent changes, no deletion) | **PASS** | Every field is captured on the transaction/line entities and surfaced in `WarehouseTransactionDetail.tsx`; no update-quantity-in-place endpoint exists — corrections only via Reversal. |
| §4 Permissions (`warehouse_worker`/`warehouse_supervisor`/`inventory_controller`, view/create/submit/approve/post/reverse/count/adjust/transfer mapped) | **PASS** | `WAREHOUSE_TRANSACTION_ACTION_ROLES` maps each action; default-deny (this round's fix) closes the one gap found. |
| §5 Sidebar navigation (accordion, one group expanded at a time, Warehouse separate from Production) | **PASS** | `Layout.tsx` accordion fix (this session, live-verified in browser: expanding one group collapses any other). `nav_group.production` remains a separate group from `nav_group.warehouses` in the same file — no mixing. |
| §6 Reporting (stock, movements, receipts/issues/transfers/adjustments/counts/reversals, scope-respecting, Excel export) | **PASS**, with a caveat | The Inventory Grid and warehouse-transaction list cover current/available/reserved stock and full movement history with Excel export. A dedicated cross-warehouse "movement activity by user/date-range" report screen was not built as a separate feature in this round — the underlying data is fully queryable (every movement is a `WarehouseTransaction`/`StockMovement` row with user/date/reason/reference) but no new aggregate report UI was added, since this directive's own architecture-governance section forbids unnecessary scope expansion and no such screen was explicitly requested as missing. Documented in `KNOWN_LIMITATIONS.md`, not treated as a blocker. |

## Explicitly not built (per the CTO's own re-confirmed scope decision this session)

Purchasing/Procurement ERP, Production/Manufacturing ERP, full General Ledger/AP-AR. These were raised again this session as a possible rebuild target, investigated against the documented Non-Goals/ADR-007, flagged as a conflict, and the CTO's own explicit decision (re-confirmed after the conflict was raised) was to keep the existing Inventory/Warehouse domain scope. Building them would have been a multi-week scope expansion, not a V1 gap.
