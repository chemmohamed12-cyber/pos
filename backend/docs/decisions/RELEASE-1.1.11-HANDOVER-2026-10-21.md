## 6. Deployment and rollback instructions (test hosting, via the existing Release Center / engine)
Prerequisites on the host: the running engine is 1.1.10 or later with company fan-out available (it is in 1.1.10); `RELEASE_STAGED_ACTIVATION=true`; absolute `PG_DUMP_BIN`/`PG_RESTORE_BIN`; free disk (the candidate copies the active tree — clean old `storage/release-staging` first, see the 1.1.7 host-cleanup notes); upload cap ≥ 6 MB.
1. Set `RELEASE_COMPANY_MIGRATIONS=dry-run`, upload the zip (Release Center → upload → full), take/link a **verified backup**, deploy once as dry-run and read the `company_fanout_plan` audit event (expect each READY Company to receive the 21 pending migrations, none `blocked`).
2. Set `RELEASE_COMPANY_MIGRATIONS=on` and deploy the same release; the engine takes a per-Company verified `pre_update` backup, migrates Companies (READY→MIGRATING→READY), swaps atomically and triggers the restart. Stop-on-first-failure; ACTIVE is untouched until the swap.
3. Verify: `/api` health, login, company selection, Treasury workspace and documents, supplier invoices; configure `RELEASE_READINESS_URL` to get `VERIFIED` instead of `DEPLOYED_UNVERIFIED`.
4. **Rollback (preferred, schema kept):** re-activate the previous slot (`app.prev-<releaseId>`, 1.1.10 — it runs unchanged on the migrated schema, proven in the rehearsal) via the Release Center rollback/LKG path; do not roll the database back. Database rollback = the 21 `down()` in reverse order (§4) on a restored copy only, and it destroys the new tables' content.
5. Never run a migration by hand or twice; never replace `DATABASE_CREDENTIAL_ENCRYPTION_KEY`/`INTEGRATION_ENCRYPTION_KEY` (existing notes).
The rehearsal installed this exact procedure (`rehearsal-script-rehearse.ps1` in the evidence folder) against isolated databases.
