## What the pattern says
* The three inventory methods behave as predicted by the N-01/N-02 idiom analysis: **with a transaction manager the guarantees hold (S1, S2: all PASS); with a plain manager the advisory lock is released at once and the read–modify–write is unserialised**, which is the same defect shape that N-02 fixed for `releaseReservedQuantity` and `fulfillReservation` by moving them to `runInTransaction`. `relocateReservedStock` and `releaseReservedQuantityForReference` still use `manager ? run(manager) : dataSource.transaction(run)`.
* `releaseReservation` (S3) is a different, smaller defect: no lock and an unconditional write, so concurrent calls all succeed and duplicate the audit row, in either style. No quantity effect was observed (the reservation ends `released`); an interaction with a concurrent fulfilment of the same reservation was **not probed**.
* The limit-gated creation paths (S4) are safe in the shape tested: the pre-check is advisory but the in-transaction `consume` is the real gate.

## Remediation (C14, authorised by the CTO on 2026-10-14) — implementation commit `354d0f7`

**Authorisation:** "Local code remediation is authorised for the six FAIL-DEFECT cases reported by T-30 on commit d68fd10." Scope kept: three methods in `inventory.service.ts` and the T-30 spec; no other behaviour, schema or caller changed.

| # | Failing case (at `d68fd10`) | Method / path | Cause | Correction |
|---|---|---|---|---|
| 1 | S1-A (plain) | `relocateReservedStock` | `manager ? run(manager) : dataSource.transaction(run)` — with a plain manager the two advisory locks are released at once and the read-modify-write of reservation rows, transfer movements and audit runs unserialised (6 of 8 succeed against 5 reserved; −1 on hand; lost update on the destination row) | `runInTransaction(this.dataSource, manager, run)` — join an active transaction, otherwise open one on the caller's manager (the rule N-02/H2 already applied to `releaseReservedQuantity` and `fulfillReservation`) |
| 2 | S1-C-A (plain) | `relocateReservedStock`, failure after the source rows moved | the same: each statement auto-commits, so the FK failure on the destination left the source reduced (5 → 3) with no movement | same single change — the whole unit is one transaction and rolls back |
| 3 | S1-D-A (plain) | `relocateReservedStock` against another relocation and `reserveStock` | the same unserialised read-modify-write (order totals 5 → 8 and 6) | same single change; the sorted lock order was already correct (no deadlock was ever observed) |
| 4 | S2-A (plain) | `releaseReservedQuantityForReference` | the same idiom (12 of 12 succeed against 5; 4 still active) | `runInTransaction`, as its twin `releaseReservedQuantity` |
| 5, 6 | S3-A (plain) and S3-B (transaction) | `releaseReservation` | no lock, and the status check and the status write were separate steps (8 of 8 succeed, 8 audit rows) — so a transaction alone did not help | runs through `runInTransaction`, takes the per-(warehouse,product) advisory lock — the key `reserveStock`, `releaseReservedQuantity`, `relocateReservedStock` and `fulfillReservation` use — and re-reads the reservation **under** the lock before the status check; the audit row is written on the same manager |

**Invariants inspected before choosing the fix.** (a) `runInTransaction` is the project's one transaction rule (`foundation/transaction/run-in-transaction.ts`); `fulfillReservation` and `releaseReservedQuantity` already use it, so the correction brings the siblings to the established invariant instead of adding a mechanism. (b) A plain manager has **no** atomicity: every statement auto-commits and an advisory transaction lock lasts one statement — the plain-versus-transaction measurements (S1, S2) show exactly that. (c) Callers that already pass a transaction manager (`returns.service.ts:425`, `work-order.service.ts:395`) are unchanged: the active transaction is joined. (d) The lock key is shared with the fulfilment path, which is what makes a release and a fulfilment of one reservation exclusive (new S3-C).

**Regression coverage** (T-30; the assertions of the six cases are unchanged — none weakened, no skip, none removed): the six original cases; **S1 now runs four independent rounds per calling style**, because the plain-manager race is probabilistic and a single round once passed by luck on the unfixed tree; **new S3-C** (4 releases against 4 fulfilments of one reservation, both styles: exactly one operation wins, and the status, dispatch movement, on-hand and audit rows agree with the winner); **new S3-D** (rollback of an outer transaction after a release restores `active` and the audit row; a retry then succeeds). Red-first: on the unfixed code the six original cases and S3-C-A/S3-C-B failed in two consecutive runs.
