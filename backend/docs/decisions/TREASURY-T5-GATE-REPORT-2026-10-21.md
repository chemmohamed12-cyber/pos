## 1. Scope
| Requirement | Status |
|---|---|
| Statement import with validation and duplicate-file detection | **Done** — arithmetic (opening + Σ lines = closing), dates inside the period, non-zero 2-decimal amounts, ≤ 5000 lines, account active + GL-mapped, file hash unique per account, **chronological and contiguous** (no overlap, no back-filling, opening = previous closing), lines already present in another statement flagged `possibleDuplicate` (never silently dropped) |
| Matching suggestions (amount, date, reference) with review of ambiguous cases | **Done** — pure rules (`bank-statement.ts`, 8 unit tests): amount must match to the cent, value date within ±5 days, reference / transaction-number evidence raises the score; outcome `suggested` / `ambiguous` / `unmatched`; **nothing is ever matched by the matcher** |
| Explicit confirmation, manual matching, undo | **Done** — `confirm` checks account, status `posted`, Σ movements = line amount to the cent, one active match per movement (**DB-enforced unique partial index**, proven under concurrency); `unmatch` needs a reason; one line may match several movements (batch deposits) |
| Unmatched items and their age; reconciliation statement | **Done** — outstanding book items and unmatched bank lines with `ageDays`; proof table (bank closing + outstanding = adjusted bank; book + bank-only = adjusted book; difference) |
| Bank fees / interest through approved accounting flows | **Done** via ordinary Treasury documents (profile reason `BANK_FEE` etc., separate approver, explicit execution), then matched — the statement itself posts nothing |
| Reconcile only when proven; controlled reversal | **Done** — all lines matched **and** difference = 0.00 to the cent, else the exact figures are returned and nothing closes; `reopen` needs a reason, audited; a reconciled statement cannot be re-matched or unmatched |
| Treasury ↔ bank book ↔ GL reconciliation | **Done at the arithmetic level** (book balance at period end from the append-only ledger, GL consistency asserted in the specs); the **GL itself is reconciled by the existing Cash/Bank↔GL run** |
| Cash sessions: opening float, count, variance, immutable close, controlled reopen | **Done** — open on cash/custody accounts only (one open session per account, DB-enforced); close snapshots the book balance under the account lock; a variance needs a reason and creates a **draft** receipt/disbursement document via the posting profile (`CASH_OVER` / `CASH_SHORT` must be mapped, else the close is refused and nothing changes); there is no edit; reopen needs a reason, is refused once the variance document is approved/executed, and cancels a still-draft correction |
| **Separation of settlement from approval/execution** | **Done** — document view carries `settlement.state` = `not_executed` / `unsettled` (executed and posted, no confirmed bank match) / `matched` (statement + line). Executing or posting never implies the bank cleared |
| Payment instruments (cheque / wallet / external rails) lifecycle | **Deliberately NOT implemented**: instrument semantics are an open owner policy (R1 `REQUEST-TREASURY_OWNER`, still PENDING) and no external integration exists; none is represented as available in the UI or API |
| Statement file formats (CSV/MT940/CAMT) | **Not implemented** — the API takes structured lines; the UI accepts pasted `date,amount,reference,description` rows. Format adapters are a later, separate item |
