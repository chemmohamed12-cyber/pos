# Authorization program — verification tools (isolated environment only)

Scripts used to produce the F1/F2 gate evidence. They talk to the isolated verification environment (backend `127.0.0.1:3601`, Postgres `127.0.0.1:5656`, `bv_*` databases) and refuse nothing by themselves, so **never point them at a shared or production host**. Test credentials are NOT stored here: export `BV_TEST_PASSWORD` for the seeded test accounts.

- `f1-http-verification.js`, `f2-http-verification.js` — real-HTTP verification of `/auth/me`, navigation, organization (F1) and Company Users / invitations / multi-role (F2).
- `ab-latency-harness.js` — interleaved A/B latency against a pre-change build on port 3602. Counts EVERY non-200 per side and `ab-aggregate.js` discards the whole run if either side saw one (a Throttler 429 is a fast response and silently biases percentiles).
- `f3-http-verification.js` — real-HTTP verification of the F3 role-management surface (custom roles, protected roles, in-use deletion, risk-aware anti-elevation with a delegated people-manager, inactive roles, audit).
- `capability-snapshot.js` — read-only snapshot of every user's effective capability map (product `AuthorizationContext`) in every READY bv Company database; run before and after a migration and diff the two JSON files to prove "no user loses access".
- `f4-http-verification.js` — real-HTTP verification of the platform plane: platform roles/capabilities, the guard matrix over real routes, escalation, support access (validation, grant, Company visibility, expiry enforced on the next request, sweeper, Company-side end), integration catalog, legacy compatibility. Creates its test identities as members of a DIFFERENT Company than the support target and removes them through the API afterwards.
- `f5-http-verification.js` — F5 runtime verification (legacy-role migration): capabilities per legacy role, menus, Company-aware `/admin/sales-reps` A/B, organization writes, custom-role capability, divergence monitor. Run once in `AUTHZ_WORKFLOW_MODE=dual` and once in `capability`; throttle-aware (register 5/min, login 10/min).
- `f6-http-verification.js` — F6 scope pilot (two branches, scoped operators with identical permissions, every pilot surface, instant grant effect, Effective Access Preview == guards, containment, audit, restore). Existing demo warehouses are linked to a test branch for the run and restored; throttle-aware.
- `closure-http-verification.js` — CTO decisions of 2026-10-07 over real HTTP: Decision 4-C (support self-grant / self-extension prohibited, support membership fixed, refusals audited) and Decision 3 (a Company provisioned through `POST /installation/companies` gets `company_admin` as initial administrator; administration without ERP power; F3 critical anti-elevation; no self-elevation of roles or scope). The bv Companies predate Decision 3 (legacy `admin`, no `company_admin` role row), so the script provisions one test Company (`Closure Co <stamp>`) per run.
- `security-mutation-verification.js` — closure Step B: scope containment / self-scope / membership removal, cross-Company A→A / A→B / B→B / B→A, support self-grant and unauthorized-Company targeting. Every refusal is bracketed by md5 fingerprints of the touched tables in Company A, Company B and the control plane: a refusal passes only with the refusal status AND zero DB change; positive controls prove the fingerprints detect real writes.
- `scoped-user-latency.js` + `scoped-user-aggregate.js` — scoped user vs administrator vs the pre-F1 build (3602), interleaved, N per endpoint, P50/P95/P99, statements per request counted on the measurement-only instance 3603; any run with a non-200 is discarded per endpoint.
