## 1. What the money does today (verified)
| Step | Mechanism | GL |
|---|---|---|
| Driver records a COD collection | `recordCollection`: Treasury `cash_in` into the vehicle's **custody Treasury account** (`cod_collection_custody`), `collections` row, event `collection.recorded` | **none by design** (ADR-042 D3: `collection.recorded` never has a GL handler) |
| Finance remits a collection | `remitCollection`: Treasury `transfer` custody → settlement account **for exactly `collection.amount`**, Customer-Ledger credit `cod_collection` (+ invoice status), event `collection.remitted` keyed `collection:<id>:remitted` | **Dr settlement account (its mapped GL) / Cr AR** — the only GL trigger |
| Reversal / return | custody-return guard refuses any shipment that already has a collection; no collection reversal exists | — |
Per-collection idempotency keys, per-collection transfer and per-collection GL event already exist: **several collections per shipment do not need a new accounting mechanism** — each one remits, credits AR and posts its own journal. The one-collection rule is only an application-level guard (no DB unique index on `collections.shipmentId`).

## 2. Operation-by-operation review and the decision taken
**(a) Multiple collections (D-2) + driver-record / cashier-confirm (D-3).** Reuse `collections` (add columns, no parallel model): `verificationStatus recorded|confirmed|rejected`, who/when, rejection reason, client idempotency key, `custodyId`. Invariant (server, serialised per shipment under the existing advisory lock): Σ(recorded+confirmed) ≤ expected COD amount; a rejected row leaves the sum. **Recording and confirmation are operational** — the physical cash is with the driver at recording (custody `cash_in` stays at record time), so confirmation posts **nothing**. Remittance (finance) keeps its path and, for a collection still in `recorded`, performs the confirmation itself (the remitter ≠ the collector) so the legacy flow is preserved. Migration backfill is a fact, not an inference: legacy rows already `remitted` → `confirmed` (finance posted them); legacy unremitted rows → `recorded`. Readers that assumed one collection per shipment (`customer-accounts.service`, `returns.service`) are updated to aggregate / use "any". **No GL change.**
**(b) Custody record.** New `shipment_custodies` (number from the numbering engine, one per shipment that actually carries cash — created lazily by the first collection or expense, never for every shipment; vehicle, driver, copied free-text branch, expected amount). Operational only; its status is derived from collections/expenses/handovers, never stored by the UI. No accounting entry of its own.
**(c) Per-line partial delivery (D-1).** New append-only `shipment_line_deliveries` (shipment line, delivered qty, returned qty, reason, actor, idempotency key) with the invariant delivered + returned ≤ shipped; "partially delivered" is **derived** (some line short) while the shipment keeps its canonical state. **Inventory/accounting: no posting in this change** — the existing `delivered` outcome still fulfils the order's reservations; per-line short-delivery stock/AR effects (credit note / return) remain the Returns Engine's job (the remainder is returned through the existing return flow). Operational record only.
**(d) Expenses (D-4, D-5).** New `custody_expenses` (custody, category code, amount, mandatory reason, incurredAt, evidence asset, status). Category → GL account comes **only** from Accounting-Policy configuration (the same `reason_map` mechanism as the Treasury disbursement profile — no hard-coded or guessed account; **fail-closed** when a category is unmapped). Approval = the existing FA-01 engine (maker ≠ checker, live permission check). Posting = a **Treasury disbursement document** from the vehicle's custody account (the existing Treasury Documents machinery: separate execute, balance check, GL event, journal), so no new posting code. Because the custody account must carry a mapped GL account for that journal, **an unmapped custody account refuses execution** (fail-closed) until finance maps it.
**(e) Handover + settlement.** `custody_handovers` (driver declaration, idempotent) + cashier confirmation (maker ≠ checker). A confirmed handover is an operational record; the **cash movement and AR credit stay with the existing remit** (finance). The reconciliation endpoint computes — on the server, from verified rows only — expected, recorded, confirmed, rejected, approved/posted expenses, handed over (declared / confirmed), remitted and the outstanding/difference, as separate lines.

## 3. Genuine accounting-policy blocker (reported, not guessed)
**Expenses paid out of collected cash versus remittance.** Remittance transfers the gross `collection.amount` from custody and credits AR gross. If an approved expense is paid from the same custody account first, the custody balance is lower than the sum still to be remitted, so the **last remit is refused for insufficient balance** (money integrity is preserved — nothing overdraws). The finance owner must decide how that case is booked: (A) remit the NET (partial transfer, AR credited gross, the expense as the difference), (B) expenses are paid from a separate float/advance and never touch collected cash, or (C) another netting rule. Until decided: expense posting is available only where the custody balance covers it, remit remains gross and fail-closed, and the reconciliation shows the expense and the remittable amount separately. **No netting journal is invented.**

## 4. Not changed
The accounting engines, the posting guard, the Collection→GL path (`collection.remitted`), the Treasury ledger invariants, the approval engine and Treasury documents are reused as they are. Free-text vehicle branch kept (D-6): no Branch entity, no branch-level security claimed.
