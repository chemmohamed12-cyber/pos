### D. PA-43 — what the code does (verified by reading; no UUID repair was run, no record touched)
1. `src/database/uuid-repair.core.ts` lists `audit_records.actorUserId` (SOFT_REFERENCES, target `users`) and `audit_records.organizationId` (target `org_units`) as columns to rewrite; `runUuidRfc4122Repair` executes `UPDATE "<table>" SET "<column>" = <newId> WHERE "<column>" = <oldId>` for every soft reference of every re-keyed row. The standalone deferred migration `tools/data-repair/deferred-migrations/1755852700000-RepairNonCompliantUuids.ts` contains the same two entries and the same loop.
2. `computeAuditHash` takes `actorUserId` and `organizationId` as inputs. Rewriting them changes what a verifier recomputes while the stored `hash`/`prevHash` stay as written: the chain would report broken at the first affected record (and, because later rows link to those hashes, `verifyChain` fails from there). The code comments deliberately exclude `audit_records.before/after` JSON as "history" but say nothing about the two hashed columns.
3. The post-repair integrity check (`verifyUuidRepairIntegrity`) contains no audit-chain verification (no reference to a chain or hash anywhere in the file), so a repair that damaged the chain would still report `passed`.
4. Triggers: the controlled flow in `DataRepairService` (create → plan → link a VERIFIED backup → execute, run on the injected ambient `DataSource`) exposed through `release.controller` endpoints under `/data-repairs`, and the deferred migration (outside `src/database/migrations`, so not run by the normal migration glob). Neither is automatic. The access control on those endpoints was not reviewed.
5. **Not established (assumptions kept separate):** whether any repair has ever run (the `data_repair_runs` table was not read — no approved read access); whether any database contains non-RFC4122 ids referenced by audit rows (counts Q0–Q6 not run); whether Company databases (as opposed to the ambient/legacy database) were ever repaired.
**Defect analysis:** a latent integrity defect in the repair tooling (impact: silent invalidation of historical audit chains; reproducible only on a disposable database with non-compliant ids — not reproduced here). **Minimum safe corrective action (bounded, not authorised, not done):** (a) keep the interim prohibition (DEC-25); (b) make `plan()` count audit rows referencing ids in the mapping and **refuse** to produce an executable plan while any exist, until a policy exists; (c) add an audit-chain verification to `verifyUuidRepairIntegrity` that fails the repair if the chain was valid before and is not after. Acceptance: a fixture database with an audit row whose actor id is non-compliant → `plan()` reports the affected count and blocks; with (c) alone, a forced repair fails verification and the run is marked failed. Historical rows are never rewritten by the fix.

### E. WP-AUD-08 — conformance of `e344ca1` to the approved decision (Option B, fail closed)
Approved decision (assignment): fail closed on detected lag; **automatic realignment is not authorised**. `e344ca1` implements **Option A**: when `nextval <= tailSeq` it calls `SELECT setval(seq, tailSeq, true)` and draws again, logging a warning; it throws `AuditSequenceLagError` only if the realignment does not move the sequence. Non-conformities (verified in the diff): (1) automatic `setval` — explicitly not authorised; (2) it needs UPDATE privilege on the sequence (a new privilege dependency); (3) the lag is **hidden** after one log line — no audit record, no distinct error, no refusal; (4) it draws `nextval` *before* checking, so even where it would refuse, a sequence value is burned (design contract C6: refusal must leave the sequence unchanged); (5) it records no `headSeq`/`nextSeq`. The acceptance spec T-27 asserts the Option A behaviour (appends *succeed* under lag, concurrent appends succeed, sequence stays advanced after rollback) and exercises fail-closed only through a mocked `setval`; it therefore **cannot serve as acceptance for Option B**. Also: no clean-snapshot evidence of T-27 exists in the repository (see §2F), and the CTO decision itself is not recorded in the repository's decision register (the closeout and register describe the choice as open) — the decision should be recorded verbatim.
**Verdict: Rework Required.** Bounded request: replace the realign branch by a pre-check that reads the sequence state without consuming it (`SELECT last_value, is_called FROM <seq>`; next value = `is_called ? last_value + increment : last_value`) under the audit lock, and throws a dedicated error (`AUDIT_SEQUENCE_LAG`, fields `headSeq`, `nextSeq`, no row data) when `next <= headSeq`; no `setval`, no write, sequence untouched. Acceptance criteria (clean-snapshot, header pinned): L1 (sequence behind) and L2 (explicit seq far above) both refused with the identifiable error and no raw `23505`; refused write leaves the sequence `last_value` unchanged; 10 repeated attempts do not drift; 20 concurrent writers under lag all refused, none out of order; after an operator realigns, 20 concurrent writers succeed with a valid chain; existing broken chain neither changed nor repaired; T-22/T-23/T-26 L0 unchanged; startup/test assertion that the audit sequence has increment 1 and cache 1; an owner and runbook for realignment named before it is enabled.
