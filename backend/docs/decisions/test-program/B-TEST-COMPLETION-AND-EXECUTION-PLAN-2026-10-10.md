# B. وثيقة استكمال التنفيذ — Test Completion & Execution Plan

الحالة: **مسودة للاعتماد — لا تنفيذ قبل الاعتماد.** جميع الأرقام الواردة أهداف مقترحة (RECOMMENDATION) وليست معايير معتمدة؛ تُعتمد قبل التشغيل ولا تُعدَّل بأثر رجعي.

## ضوابط عامة (تنطبق على الاختبارين)
- بيئة معزولة فقط (PG معزول + backend مبني من commit مثبت). ممنوع: الاستضافة الإنتاجية، `daii_dev`، أي قاعدة مشتركة.
- لا تعديل لكود الإنتاج أو القواعد لتسهيل النجاح؛ أي عيب يُسجَّل ويُصلح بقرار منفصل ثم يعاد الاختبار.
- كل non-200 يُعدّ ويُصنَّف (429 من Throttler، 404 رفض صلاحية، 5xx…) ولا تُحسب النتيجة إن شُوِّهت به (درس `ab-latency-harness`).
- حماية البيانات: قاعدة قالب مجمّدة (snapshot) تُستنسخ لكل جولة؛ بصمات md5 للجداول المعنية قبل وبعد؛ تنظيف بحذف قواعد الاختبار المسماة صراحة فقط (لا حذف شامل).
- لا تحميل أدوات من الإنترنت دون إذن صريح بالاسم والمصدر والحجم.

---
## 1. الاختبار الأول — Platform Capacity & Scalability
**1. الهدف والنطاق:** منحنى الأداء والاستقرار مقابل (عدد الشركات × المستخدمين المتزامنين × معدل الطلبات)، نقطة التدهور، وسلامة العزل تحت الحمل. خارج النطاق: الاستضافة الإنتاجية، حدود مزود الاستضافة.
**2. البيئة والبيانات وشروط البداية:** (يلزم قرار) مواصفات مضيف ممثلة؛ PG بإعدادات موثقة (max_connections, shared_buffers, pool)؛ backend بنفس `COMPANY_DB_MODE`؛ N شركات تُنشأ عبر `POST /installation/companies` (المسار الحقيقي) وتُملأ بالبيانات عبر الواجهة البرمجية (لا إدخال مباشر في DB)؛ لكل شركة علامات فريدة (markers) في بياناتها لكشف التسرب؛ شرط البداية: إصدار مثبت، قياس خط أساس للجهاز فارغًا، Throttler بإعداد موثق.
**3. الخطوات بالترتيب:**
 1. معايرة: خط أساس مستخدم واحد (يعيد قياسات 1.1.6 على نفس البيئة).
 2. شركة واحدة: ارتفاع تدريجي للمستخدمين 10→50→100→250→500→1000 (مقترح)، كل مرحلة ≥10 دقائق + 2 دقيقة تسخين.
 3. شركات متعددة: N = 1, 5, 10, 25, 50 (مقترح) بنفس الحمل لكل شركة؛ ثم «جار صاخب»: شركة واحدة بحمل 10× والبقية عادية.
 4. حمل مختلط (قراءات/كتابات/تقارير/تسجيل دخول/تجديد token).
 5. تحمل (soak) ≥ 2 ساعة عند 70% من النقطة المستقرة.
 6. تجاوز الحد حتى التدهور/الفشل وتسجيل السبب.
**4. السيناريوهات:** قراءات قوائم، إنشاء مستند، اعتماد، حركة مخزون، تحصيل، تقرير، إنشاء شركة أثناء الحمل، Release/تجديد اتصال.
**5. الأدوات:** مولّد حمل (k6 أو بديل — بإذن)، مجمّع نتائج يعدّ كل non-200، عدادات CPU/ذاكرة لعملية Node والمضيف، `pg_stat_activity`/`pg_stat_database`/قفل/اتصالات، سجل أخطاء backend، فاحص التسرب (markers + بصمات).
**6. معايير النجاح/الفشل/الإيقاف (مقترحة للاعتماد):** نجاح مرحلة: p95 ≤ الحد المعتمد، أخطاء 5xx = 0 (ومعدل خطأ كلي ≤ حد معتمد)، تسرب = 0، موارد دون حد معتمد. **أي تسرب بيانات = فشل فوري وإيقاف كل التشغيل.** إيقاف: 5xx متواصلة، اتصالات PG > 90% من الحد، استنزاف ذاكرة، فشل التنظيف.
**7. إعادة الاختبار:** نفس البيئة والإصدار والبيانات من الـ snapshot؛ تكرار 3 مرات؛ يُعتمد الأسوأ للحدود؛ بعد أي إصلاح إعادة المرحلة الفاشلة وما يليها.
**8. حماية البيانات والتنظيف:** كل قواعد الاختبار بأسماء ببادئة صريحة؛ يُحذف المسمّى فقط؛ إثبات عدم لمس `daii_dev` بقياس قبل/بعد.
**9. المخرجات:** تقرير بيئة، جدول مراحل (شركات/مستخدمون/معدل/مدة)، منحنيات p50/p95/p99/أخطاء/موارد، نقطة التدهور وسببها، نتيجة فحص التسرب، الخام (CSV/JSON) وسكربتات قابلة للإعادة، **حدود القدرة المدعومة بالقياس فقط**.
**10. شروط الإغلاق:** كل المراحل نُفذت بمعايير معتمدة سلفًا، تسرب = 0، نتائج مكررة 3 مرات، مراجعة والتقاط الفجوات. الجهة المعتمدة: CTO. لا يُعلن حد أقصى للشركات إلا من هذه النتائج.

## 2. الاختبار الثاني — Business Integrity & Adversarial Testing
**1. الهدف والنطاق:** المحاور السبعة في التقرير A §2. كل سيناريو: «مستخدم مسيء» يحاول تجاوز القاعدة.
**2. البيئة والبيانات:** استنساخ من قاعدة T0 النظيفة (`T0-CLEAN-COMPANY-BASELINE`) + شركتان A وB، مستخدمون بأدوار: ضعيف الصلاحية، مدير، محدد النطاق، مستخدم شركة أخرى.
**3. الخطوات:** (أ) مسح تفصيلي للتغطية الحالية لكل محور وتحويلها إلى سجل سيناريوهات؛ (ب) كتابة السيناريوهات الناقصة؛ (ج) تنفيذ عبر HTTP حقيقي (نمط `security-mutation-verification.js`)؛ (د) جمع الأدلة؛ (هـ) mutation: إفساد القاعدة عمدًا في نسخة معزولة للتأكد أن الاختبار يفشل.
**4. السيناريوهات (قالب إلزامي لكل حالة):** ID · المحور · الحالة الابتدائية (بصمة) · الهوية والصلاحيات · الطلب · المتوقع · الفعلي · أثر DB (بصمات قبل/بعد) · دليل التدقيق (سجل بالمنفذ/الوقت/التغيير) · الحالة.
 - **المخزون:** صرف > المتاح؛ كمية سالبة/صفر؛ تعديل رصيد مباشر؛ تكرار نفس الحركة (idempotency).
 - **الاستلام/التحويل/الشحن:** صرف من مخزون غير مملوك؛ استخدام محجوز مرتين؛ تخطي/تكرار مرحلة؛ تحويل داخلي لا يُحتسب بيعًا؛ مرتجع > min(sold, shipped).
 - **المبيعات/الاعتماد:** تجاوز الاعتماد؛ تعديل كمية بعد الاعتماد يعيد فحص التوافر؛ اعتماد ذاتي.
 - **الخزينة:** تحصيل ≠ المبلغ؛ تحصيل/ترحيل مكرر؛ إتمام دون شروط؛ تقييد غير متوازن.
 - **الصلاحيات/العزل:** رفض على API لكل endpoint حساس؛ تغيير معرّف الشركة/المورد (IDOR)؛ أزرار مخفية لكن الطلب المباشر يُرفض؛ A↔B.
 - **التدقيق:** حذف/تعديل حركة مسجلة؛ تطابق الأرصدة مع الحركات؛ تسجيل المنفذ والوقت والتغيير؛ سلامة السلسلة.
 - **التزامن:** N طلبات متزامنة على نفس الرصيد/التحصيل؛ إعادة إرسال؛ deadlock retry.
**5. الأدوات:** نمط authz-tools (HTTP + بصمات md5 + عدّ non-200)، jest `--runInBand` لسيناريوهات DB، استعلامات تحقق للأرصدة، مولد تزامن بسيط.
**6. معايير النجاح/الفشل/الإيقاف:** النجاح = رفض العملية غير المسموحة **دون أثر**: بصمات الجداول متطابقة قبل/بعد، لا قيد ناقص، دفتر الحركات والأرصدة متطابقان، سجل التدقيق يسجل المحاولة المرفوضة حيث يلزم، وتحت التزامن لا تتجاوز الأرصدة المتاح ولا تتكرر الحركة. الفشل = أي أثر أو قبول. الإيقاف: أي كسر في سلامة DB أو عزل الشركات.
**7. إعادة الاختبار:** كل عيب يحمل ID؛ بعد الإصلاح (بقرار منفصل) يُعاد السيناريو + مجموعة الانحدار للمحور؛ لا تعديل لمعيار القبول.
**8. حماية البيانات:** استنساخ قاعدة لكل تشغيل؛ استعادة baseline وتحقق بالبصمة؛ حذف المسمّى فقط.
**9. المخرجات:** سجل سيناريوهات (جدول حسب القالب)، سجلات HTTP، بصمات، لقطات سجلات التدقيق، تقرير عيوب، تقرير تغطية لكل محور.
**10. شروط الإغلاق:** كل سيناريو في الحزمة المعتمدة PASS بأدلته أو عيب موثق بقرار؛ مراجعة CTO. لا يقبل إغلاق بنجاح البناء أو اختبارات لا تغطي النطاق.

## 3. الاختبار الثالث
لا خطة. **تعريفه غير محسوم**. مطلوب من المراجع: الاسم/المرجع الأصلي، الهدف، معايير القبول، وأي نتائج سابقة. حتى ذلك الحين لا نطاق ولا تنفيذ.

## 4. ترتيب التنفيذ المقترح بعد الاعتماد
1) حسم الاختبار الثالث وبيئة وأهداف الاختبار 1 (قرارات فقط). 2) الاختبار 2: مسح وسجل سيناريوهات (قراءة فقط) ثم التنفيذ حسب المخاطر: مال/مخزون ثم تزامن ثم تدقيق. 3) الاختبار 1 بعد اعتماد البيئة والمعايير. ملاحظة: مسألة انقطاع سلسلة التدقيق في الإنتاج وقرارات الأسرار مسارات منفصلة.
