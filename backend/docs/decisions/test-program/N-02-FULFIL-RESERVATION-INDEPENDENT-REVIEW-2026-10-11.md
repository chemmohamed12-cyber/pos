## 2. What was inspected beyond test results
1. **The diff itself** (`git diff 7097796 b591d1f -- inventory.service.ts`): the only product change between `a6002fa` and `b591d1f` outside the LA-1 track's files is this file (11/2). `git diff --name-only a6002fa b591d1f` for non-test source: `inventory.service.ts`, `biz-run.js`, plus the LA-1 commit's four files (schedulers, installation-audit controller, `company-lifecycle-admission.ts`) — none touch inventory.
2. **Lock inventory** (`grep pg_advisory_xact_lock`): reservation key `"<warehouseId>:<productId>"` (reserveStock `:815`, release `:1406`, `:1470`, the patch `:1543`, assemble `:1646`), valuation key `valuation:<W>:<P>` (moving-average engine `:75, :143, :202, :267, :354`), `warehouse_transaction_post:<id>` and pair keys (warehouse transactions `:535, :549`), the global audit-chain key (`audit.service.ts:62`). The patch uses **the same reservation key** as `reserveStock` / `releaseReservedQuantity`, so fulfilment now serialises against reserving and releasing the same (warehouse, product).
3. **Order of acquisition inside a fulfilment:** reservation key → (inside `recordMovement`) valuation key of the dispatch warehouse → audit-chain key. This is the same direction `reserveStock` uses (reservation key → audit). No path was found that takes a valuation or audit lock *before* a reservation key for the same operation.
4. **Transaction ownership:** `runInTransaction` joins an active transaction or opens one on the caller's manager; `fulfillReservationsForOrder` passes its manager `m` into `fulfillReservation`, which therefore joins (no nested transaction, one connection, one commit). With a plain manager the whole order is one transaction.
5. **Re-read after lock:** the first read only learns `(warehouseId, productId)`; the second read happens under the lock, so under READ COMMITTED (the default; no `SET TRANSACTION ISOLATION LEVEL` found in `src/`) a second caller sees `fulfilled` after the first commits and gets `409`.
6. **Reservation/movement consistency:** the status flip and the movement are in the same transaction as the lock; a failing movement rolls the flip back (case C, FK violation) and an outer rollback restores the reservation (case D).
7. **Callers:** `fulfillReservation` is called only inside `fulfillReservationsForOrder`; that is called from `delivery.service.recordOutcome` inside its own transaction (`txManager`) and through the inventory contract. Reachability of the original double-dispatch on real paths is therefore **narrow**: a duplicate "delivered" outcome first runs `shipments.transitionShipment(…, txManager)`, which (since N-01) takes the process-instance row lock and refuses an illegal second transition *before* the fulfilment is reached (INFERRED from the code order; not exercised by a delivery-level concurrency test). The service-level defect was real (T-20 H3 baseline) but its practical exposure through delivery was limited.
8. **Behaviour change:** a repeated fulfilment of an already-fulfilled reservation (or order) now ends in `409` instead of posting a second dispatch. Callers that retry must treat 409 as "already done"; the only in-repo caller runs inside a transaction that aborts on it.

## 4. Residual risks (none closed by the evidence)
- **Deadlock potential (INFERRED, not tested):** the global audit-chain lock is held until the end of a transaction. A multi-line order fulfilment takes, per line, the reservation key → valuation key → audit key. Two concurrent order-level fulfilments of **different** orders with overlapping products in opposite order (A: P1 then P2; B: P2 then P1) can wait on each other (A holds the audit lock and waits for P2's key; B holds P2's key and waits for the audit lock). PostgreSQL detects it and aborts one transaction (SQLSTATE 40P01) — a loud, retryable failure, not corruption — and the same cycle existed before the patch through the valuation keys. Case F proves 6 independent single-line fulfilments do not deadlock; no test covers overlapping multi-line orders. A probe is recommended before any claim of deadlock-freedom.
- **Isolation level assumption:** correctness of the re-read relies on READ COMMITTED; a caller running the same transaction under REPEATABLE READ/SERIALIZABLE would not see the first commit.
- **Warehouse override:** the reservation key uses the reservation's warehouse, the movement uses `warehouseIdOverride`; serialisation of two fulfilments into the same override warehouse relies on the valuation lock inside `recordMovement`, not on the reservation key (sufficient, but indirect).
- **F-AUD-003 (separate, not N-02):** a rolled-back transaction that wrote an audit record permanently breaks the audit hash chain. Independently confirmed from the code: `audit_records.seq` is `SERIAL` (`CreateAuditRecords`: `"seq" SERIAL PRIMARY KEY`; entity `@PrimaryGeneratedColumn()`), the hash is computed with `MAX(seq)+1`, and a rolled-back insert burns a sequence value. It is a pre-existing defect that the new case D merely exposes; it may also explain unresolved "seq 1" observations on hosts (D-9) — unverified. Fix is the verification session's pending T-23 work and is to be reviewed separately.
- Not covered: multi-instance operation, concurrency above 8-way, delivery/shipment end-to-end concurrency, hosting.
