Status: **documentation only — no guard change, no broad administrative operation authorised or performed.** Each statement below was evaluated against the real guard policy (`checkAdminStatement` + `checkStatement`, cluster 127.0.0.1:5546, entry `dedicated-5546-biz`) on 2026-10-11; results are facts, not assumptions.

## C. Cases that need a decision (bring-back list)
1. **`saas-characterization.helpers.ts` group (6 specs: `module-add-existing-company`, `new-company-default-administrator`, `provisioning-lifecycle`, `ui-created-company-admin`, `limits-scope`, `release-migration-registry`).** Two independent blockers, both test-side: (a) `assertIsolatedInstance()` accepts only port 5544 (the superseded cluster); (b) the helper terminates backends with the refused `pg_terminate_backend` statement before a non-FORCE drop. **A no-guard-change adaptation exists:** replace (b) by the already-allowed `DROP DATABASE IF EXISTS … WITH (FORCE)` and extend (a) to the approved port with the namespace on the fixed names. It is not applied here because the directive asks for a narrow decision on `pg_terminate_backend`; the guard stays untouched either way. *Decision requested:* approve this test-helper adaptation (recommended; no new privilege).
2. **Role-creating specs (3: `company-database-allocation.http`, `company-registry.controller.database-creation`, `company-database-pool.full-flow`).** They need `CREATE ROLE` / `GRANT` / `DROP ROLE` (and, for one, `CREATE DATABASE … OWNER`). Required privilege: the test role would need `CREATEROLE`, which the least-privilege role `daii_biz_test` deliberately does not have (non-superuser, CREATEDB only). Targets: roles named `daii_test_nocreatedb_<6 hex>` / `daii_pool_app_<6 hex>` (they do not follow the `daii_test_biz_tNN_` shape). Isolation guarantee options: a role-name pattern entry limited to `^daii_test_biz_t[0-9]{2}_role_[a-z0-9]+$` (after renaming the roles in the specs), CREATEROLE only on a separate bootstrap-owned cluster role used by the administrative connection — **or** keep these three NOT RUN. Granting CREATEROLE to the test role widens its blast radius to every role in the cluster (including `daii_bootstrap`), so this is not recommended without a dedicated, throw-away cluster for these three specs.
3. **Product-named databases (the same 3 specs).** The allocator creates `company_<uuid>`; the guard (correctly) refuses it. A narrow, testable alternative is to run these specs against `COMPANY_DB_MODE=pool` with pre-created approved-name databases (the full-flow/multi-process specs already do), leaving only the role statements as the open point.
4. **Held:** `company-audit-access.real-pg.spec.ts` — uncommitted edits by the other track; untouched.
