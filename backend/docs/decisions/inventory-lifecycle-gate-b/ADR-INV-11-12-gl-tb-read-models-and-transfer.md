# ADR-INV-11 and ADR-INV-12 - General Ledger / Trial Balance read models, and the transfer model

**Status: PROPOSED (Gate B) - awaiting CTO review.** **Answers:** D-INV-11, D-INV-12. **Gate A evidence:** G-GL-1, G-TB-1, G-TRF-1. **Found during Gate B (code-evidenced):** G-TB-2 - the Trial Balance row click navigates to `/accounting/ledger?accountId=...` **without the `from`/`to` period** (`TrialBalance.tsx:96`) and the General Ledger page reads only `accountId` from the URL (`GeneralLedger.tsx`), so the drill-down loses the period and shows a different window than the row it came from.

---
## ADR-INV-11 - GL and TB read models
### Decision (all additive; the existing response fields keep their meaning)
**General Ledger (`GET /accounting/ledger/:accountId`)** - each line additionally returns `journalEntryId` (already selected), `entryStatus` (`POSTED | REVERSED`), `sourceType`, `financialEventId`, and, for event-sourced lines, the **source document reference** read from the financial event payload (`referenceType` and `referenceId` as the inventory events already carry them: warehouse document, opening batch, goods receipt, sales return); the document **number** is resolved lazily by the client from the owning module's own endpoint, so accounting never reads another module's tables. Accounting reads only its own tables and the event payload (no cross-module table read). The screen shows source, status, and links: entry number -> `/accounting/journals/:id` (exists), source document -> its page, "event" -> Financial Events. The page now **reads `from`, `to`, `accountId` from the URL** and writes them back, so TB -> GL keeps account and period. A read never creates or changes a journal (unchanged).
**Trial Balance (`GET /accounting/trial-balance`)** - the **existing payload and the locked gross totals stay byte-compatible** (the closing snapshot signs `totalDebitBase/totalCreditBase`; the F11 footer fields stay). A new query mode `mode=periodic` returns per account `openingBase`, `periodDebitBase`, `periodCreditBase`, `closingBase` (opening = everything strictly before `from`, as the account ledger already computes; closing = opening + period), includes accounts that have an opening balance **or** period activity (the current query drops accounts whose window net is zero), plus totals for each of the four columns and a `balanced` flag that tests **opening**, **period** and **closing** independently (closing debits = closing credits; period debits = period credits). Also returned: `asOfLastPostedAt` (the latest posted journal time in scope), `pendingEvents` / `rejectedEvents` (from ADR-INV-10) so a report states whether it is complete, and the filters echoed back. The TB screen switches to `periodic` mode, keeps the existing footer behaviour, and drills to the GL with `accountId`, `from` and `to`.
Account hierarchy (gross vs detail): the chart of accounts already has parents (`reparent`); the periodic TB rolls children up with a `level` / `parentId` so the screen can show group totals and expand to detail, using the existing chart structure only.
No inventory amount is ever added to the TB from the inventory screens: the balance source remains the posted journals.

### Impact / compatibility / rollback / tests
Backend: `LedgerService` gets one new method (the existing `getTrialBalance`/`getTrialBalanceReport` untouched), controller query flag, DTO additions; frontend: two pages and drill links; terminology rows. No schema. Rollback = default mode unchanged. Tests: periodic TB for a period with opening activity: opening + period = closing per account and in total; each of the three balance tests; zero-net accounts with activity appear; `mode` absent returns exactly today's payload (golden test, including the closing-snapshot input); GL line source/status correct for an opening batch, a manual receipt, a dispatch and a reversal; REVERSED entries stay visible with both sets of lines; URL round trip keeps account and period; unposted/rejected events never appear as posted lines; A/B isolation.

## ADR-INV-12 - Transfers (decision: keep Model A, immediate transfer)
### Decision
Keep the current design: a transfer **document** is approved by a supervisor and then posts **both legs atomically** (`transfer_out` negative at the source, `transfer_in` positive at the destination, both with `referenceType = 'warehouse_transaction'` and the same `referenceId`), valuation is carried at the source average, and **no journal** is posted (one central inventory account). This already prevents unjustified quantity (the receipt leg cannot exist without its dispatch leg, and the source must have the available quantity) and gives the receiving-to-sending link the directive asks for (same document id on both legs, verified in the Gate A probe O7). An **in-transit** state is *not* introduced unless the business shows a need (stock leaving a warehouse before arrival, long transit, separate receiving custody); if it does, it is a separate ADR using two documents, not a change to this one.
### Reinforcements (no behaviour change)
- A read-model/diagnostic check "transfer legs": every `transfer_out` has a matching `transfer_in` of equal quantity under the same document id, and the valuation carried equals the value removed (added to the reconciliation categories as `transfer_leg_mismatch`, expected 0).
- A transfer from a source **without valuation** moves quantity without value (Gate A O7). The document remains allowed (non-blocking operations were the D3 choice), but it now raises a visible warning at approval ("source has no valuation: quantity will carry no value") and the quantity-without-value query (Q1) lists it. Making it a hard stop is a separate, reversible option for the CTO (flag `inventory.transfer_requires_valuation`).
### Impact / tests
No schema, no contract change. Tests: both legs same document id and equal quantity; no journal; company total valuation unchanged before/after; source shortage rejects with nothing written; the warning appears; the reconciliation leg check detects a deliberately orphaned leg.
