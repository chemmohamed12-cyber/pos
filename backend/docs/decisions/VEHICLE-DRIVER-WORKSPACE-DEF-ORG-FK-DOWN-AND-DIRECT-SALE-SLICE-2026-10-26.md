## 1. DEF-ORG-FK-DOWN — `org_units` parent foreign key after rollback
**Observed (rehearsal on the 1.1.13 engine, 13 migrations reverted on a clone):** the schema signature after `down()` differs from the 1.1.13 baseline in exactly one constraint: baseline `org_units_parentId_fkey FOREIGN KEY ("parentId") REFERENCES org_units(id) ON DELETE CASCADE`; after rollback `FK_org_units_parent … ON DELETE RESTRICT`. Table/column/index/constraint counts are identical; every other object (including all five vehicle-workspace migrations and the direct-sale migration) reverts byte-exactly.
**Responsible migration and transition:** `core/1790021000000-OrgUnitLifecycle` (feature/org-structure-gate0, org-engine Stage 1). `up()` replaces the CASCADE parent FK by `FK_org_units_parent … ON DELETE RESTRICT`; `down()` removes `status`, `archivedAt` and the single-root index and **deliberately leaves the FK at RESTRICT** — its own comment: *re-introducing cascade deletion of a referenced subtree would be the unsafe direction*.
**Intended deletion invariant (established before any code change):** a unit that has children (and, through them, documents pointing at them) can never be deleted by deleting its parent; only a leaf can be deleted; units that documents point to are archived. The invariant must hold both with and without the org-engine migration applied. **Therefore the rollback is NOT a defect in behaviour: restoring CASCADE would weaken deletion protection, which the directive forbids.**
**Classification:** schema reversibility is *not byte-exact by design* for this one constraint (hardening is one-way). Status: **ACCEPTED EXCEPTION — documented, tested, no code change.** The rollback rehearsal's "down == baseline" check therefore carries a named exception: `org_units` parent FK (CASCADE→RESTRICT). Owner: org-structure team (they may choose to also record the exception in their release notes).
**Evidence**
- Up / no-op / down / up on isolated disposable databases (`daii_test_biz_t97_down_*`, 1.1.13 baseline reverted by 13 migrations): re-up executes the 13 migrations (320 → 333); the resulting schema signature equals the **first** upgrade's signature (`dc688a33…` platform, `6d877cca…` Company); a second run is a no-op (333 → 333, success); in both states the FK is RESTRICT, deleting a parent with a child is refused, deleting a leaf works (`updownup-*.json`, `after-reup-*.json`).
- New automated spec `org-units-parent-fk.rollback.real-pg.spec.ts` (integrated branch): R1 UP → RESTRICT and protection; R2 DOWN → columns/index removed, **still RESTRICT, never CASCADE**, protection holds; R3 UP again idempotent (one FK, same definition) and a repeat run changes nothing.
**Schema vs data reversibility:** the migrations of this work are additive. Reverting them drops the new tables/columns **with their data** (collections' confirmation history, custody records, line events, expense claims, handovers, the float column, org units' status). For data-bearing Company databases the approved recovery is therefore **application rollback with the schema kept** (proved: previous slot runs on the upgraded schema) and, where a database rollback is truly required, the **verified per-Company restore point the release engine takes before migrating** (backup-restore), not `down()`.
