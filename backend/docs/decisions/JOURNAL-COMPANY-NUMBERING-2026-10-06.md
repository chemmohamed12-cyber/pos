# Company-scoped journal numbering — blocker found by Browser Verification #1 (2026-10-06)

**Status: VERIFIED / CLOSED (CTO, 2026-10-06). FIXED, REAL-PG VERIFIED and LIVE-VERIFIED in a Company provisioned through the real API. Scope authorised: "fix only Company-scoped Journal Numbering Registration". UAT verification of the program stays pending (section 6).**

## 1. Defect
Posting any journal in a freshly provisioned Company database failed: `No numbering sequence registered for document type "accounting_journal_entry"`. Under Model B each Company database owns its own `numbering_sequences` table, but `JournalEntryService.onModuleInit` (via `ensureNumberingRegistered`) registers the JV sequence only on the AMBIENT database at boot, and `postEntry` then drew the number from the Company manager without registering it there; nothing in Company provisioning seeds it. Every real-PG spec masked this by registering the sequence by hand in its setup. It also broke EVENT-DRIVEN GL posting: in the browser run the on-account payment's `finance.payment.recorded` event ended `REJECTED` ("posting gate rejected: No numbering sequence registered…").

## 2. Root cause and decision
The registration was written for the single-database era (ambient only); the draw was already inside the Company transaction (ADR-035 D8) but the sequence existence was never ensured on that manager. Every other numbered document registers its sequence on the manager it draws from just before the draw (`registerDocumentType(type, prefix, includeYear, manager)`) — that is the established pattern, and it is applied here.

## 3. Fix (smallest blast radius; numbering architecture unchanged)
`backend/src/domains/accounting/application/journal-entry.service.ts` — new private `ensureCompanyNumbering(txManager)` called in `postEntry` immediately before `getNextNumber`: if the Company's own `numbering_sequences` has no `accounting_journal_entry` row, take a transaction-scoped advisory lock and `registerDocumentType(…, txManager)` (idempotent, re-checked under the lock). Properties: per-Company, lazy, on the manager the number is drawn from; **no fallback to the ambient database; no shared/global sequence; the Platform database is never a numbering source; no migration; no change to existing Companies' behaviour** (a Company that already has the sequence takes the no-op path; the ambient flow is unchanged). The advisory lock only matters for the very first post(s) in a Company; the draw itself already serialises posting per Company through the sequence row's FOR UPDATE, so no new serialisation is introduced.

## 4. Verification
**Spec** `accounting/interface/journal-numbering.company-isolation.spec.ts` — **5/5**, real PostgreSQL, two Company databases built by the real migration/provisioning pipeline, **NOTHING registers a journal sequence (setup or tests) and `JournalEntryService.onModuleInit` is not called**: (0) precondition — no journal sequence in A, B or the ambient DB; (1) Company A: a real manual journal is created and POSTED → `JV-<year>-000001`, the next → `000002`, A's sequence row = {JV, includeYear, lastNumber 2}, B untouched, B's DataSource never requested; (2) Company B: starts at `000001` (does not continue A's count), and **two simultaneous first posts in B both succeed** with distinct numbers `000001/000002` (race-safe registration), A's counter unchanged; (3) EVENT-DRIVEN: `finance.payment.recorded` ingested in A → `POSTED` journal numbered `000003` from A's sequence (B still at 2); (4) isolation — the ambient/Platform DB has no journal sequence and no journal entries. **The same spec run against the pre-fix service fails 4/5 with the original error** (precondition passes) — the spec reproduces the defect.
**Live (real app, isolated environment, no SQL):** a brand-new Company provisioned through `POST /installation/companies` (209 migrations, READY), starter chart imported, fiscal year created and activated through the API, then two manual journals created and posted → **JV-2026-000001, JV-2026-000002**; the Company's own database holds the sequence (lastNumber 2), the other Company's database holds its own (1) and the ambient control-plane DB holds only its boot-time registration with lastNumber 0. In a second brand-new Company an on-account customer payment (CUS-01) produced a **POSTED `finance.payment.recorded` event with journal JV-2026-000001 (source FINANCIAL_EVENT)** — the event-driven path works end to end from a fresh provisioning.
**Regression (one serial run on the isolated seeded PG, 33 suites):** **205/220 first run (+1 skipped, T0 baseline by design)**; the 14 failures are ALL in four suites that need other sessions' manufacturing migrations the isolated ambient DB does not have (`routings` relation missing: `work-order`, `work-order-phase3-e2e`, `wip-reconciliation`, `f03-deadlock-retry-verification`) — classification: **pre-existing / infrastructure, not caused by this change** (identical failures before it). Passed in the same run: general-ledger 9, event-engine 8, inventory-posting 9, manual-receipt 12, returns-accounting 12, supplier-invoice-ppv-vat 16, treasury-bank-leg 7, subledger-controllers 5, fixed-asset ×4 specs (4+3+5+5), on-account-payment 7, database-provisioning 4, company-lifecycle-layer1 10, grni 2+3, closing-snapshot 4+3, fiscal-period-closing 4, payroll GL e2e 4 and the rest of the set. **Not a full-repository regression.**

## 5. Existing data — CTO clarification (2026-10-06): no repair, no replay, no impact assessment
The defect appeared only in test / disposable environments; **no real financial data was affected**. The CTO ruled: **no Financial Event replay, no data repair, no change to old data, no reconciliation recovery for this defect.** (An earlier message asked for a read-only impact assessment of REJECTED events; the later clarification supersedes it and none was performed.) The REJECTED events seen in the throw-away verification environment are test artefacts of the pre-fix code. The ambient database still registers its own sequence at boot (unchanged); it is not used for Company numbering.
Rule recorded by the CTO: a test failure on disposable data is a **software defect**, not a Data Integrity Incident, unless it is proven on real production data.
