## Root causes of the host screenshots (reproduced locally with the 1.1.12 package: evidence G0)
- **A. stale in-flight release row.** The catch-up guard refused whenever ANY release row was `deploying` / `migrating` / `health_checking`. The host still has a row of an old version stuck in such a state (the 1.1.6 deploy the host process cut off; `reconcileInterruptedDeploys` leaves another version's row for manual review). It blocked every catch-up forever ("A deploy is in progress; catch-up refuses to run next to it.", HTTP 409 - so pressing OK in the confirmation changed nothing).
- **B. the schema-check child process fails on the host and its reason was invisible.** The check runs `node -e <program>` as a child process. On the host it failed with no stderr; the report showed only the echoed command line because `execFile`'s message embeds the whole command and was cut. The real cause (exit code / signal) is therefore NOT known; a host process / memory limit killing the child is the likely class. The gate (correctly) treats an unverified schema as a blocker.
- (The 503 `COMPANY_SCHEMA_BEHIND` on Company screens is the intended interim guard.)

## Patch in 1.1.13 (3 behaviours; dist differs from 1.1.12 only in catch-up, fan-out, schema-check, release-execution and the new operation lock)
1. Catch-up ignores in-flight rows of a version **older than or equal to** the live build; a **newer** version in flight still refuses. Ignored rows are logged.
2. A failed schema check reports **exit code / signal / timeout / start error / stderr tail** - never the echoed command, never credentials - and is never "clean" (`ran:false`).
3. **In-process fallback** when the child cannot run and the checked build is the running build (catch-up of the installed release): the same read-only check runs in the application. A real-Postgres spec runs both implementations on the same databases and requires identical findings. The deploy-time check of a candidate never uses the fallback.
4. **Operation lock** (process-wide, taken before any await): a deploy is refused while a catch-up runs and a catch-up is refused while a deploy runs, in addition to "one catch-up at a time" and the release-row guard for a newer in-flight version.

## Exact host steps (owner; NOT authorized, NOT executed)
**Facts the steps rely on:** the host runs the **1.1.12 engine** with `RELEASE_COMPANY_MIGRATIONS` unset, which for 1.1.12 means `on`. A 1.1.13 deploy is therefore planned by 1.1.12 code: it will take a verified restore point per lagging Company and migrate them (`xnexdrgr_daii_c01`, `xnexdrgr_daii_c02`) BEFORE the swap (G3). That is a change from the earlier "deploy first, explicit catch-up after" plan and needs a CTO decision. The 1.1.12 engine also runs the schema check, as a child process, on the candidate; if the host's child process fails the same way as for the installed root, the gate **blocks the deploy before any change**.
0. (read-only, recommended before anything) On the host, from the application directory, run the same node binary with `-e "console.log(1)"` and note cPanel/CloudLinux limits (memory, processes). Send the output: it identifies cause B.
1. Verify the file: `sha256sum Daii-Release-v1.1.13-2026-10-21.zip` must equal `351922653e672ad7f9dcedd3bce2acaceaec9299fdf325babaa1ad320f7f6b60`.
2. Release Center -> upload the zip (type *full*): release `1.1.13` `validated`. Create a backup, wait for `completed/verified`, link it (`backup_verified`).
3. **Decision point:** if step 0 shows the child process cannot run, the 1.1.12 gate will refuse the deploy (nothing changed, release stays `backup_verified`). Continuing then requires `RELEASE_COMPANY_SCHEMA_CHECK=report` in the Node.js App variables (an unverified schema becomes a warning) - a hosting setting change needing separate approval. Do not set anything else (`RELEASE_COMPANY_MIGRATIONS` stays unset).
4. Deploy. Expected: `succeeded`, platform 320, and (engine behaviour) both Companies 320.
5. Verify: Release Center "Company databases vs the installed build" -> *Check now* -> "Every Company is current"; Warehouse overview, Cash sessions, Supplier invoices open. If instead a Company is still behind, use the explicit action now available in 1.1.13: *Catch up ...*, the confirmation must list exactly the databases still pending (host: `xnexdrgr_daii_c01` / `xnexdrgr_daii_c02`), expect `SUCCESS`, `stillPending {}`.
**Stop conditions (send the result, do nothing else):** upload validation error; deploy `failed` or refused by the gate (read `errorMessage`; no Company is touched by a refused gate; if migrations had run the message says `ACTIVATION_FAILED_AFTER_MIGRATIONS` and the old application keeps serving on the advanced expand-only schema); catch-up `FAILED` or a refusal (read `failed[].company` / `error`); anything unexpected. No Stage B, manual SQL, direct migration commands, or edit of the stale 1.1.6 row.
**Rollback:** application: Release Center rollback to the previous slot (1.1.12 / 1.1.11 run unchanged on the advanced schema - proven in the earlier rehearsals); databases: forward-only, restore only a damaged Company from its per-Company restore point.
**Alternative without a new deploy (needs explicit authorization):** correct the single stale 1.1.6 release row, then run the already-live 1.1.12 catch-up; because the check cannot run it would report `FAILED` although the migrations were applied.
