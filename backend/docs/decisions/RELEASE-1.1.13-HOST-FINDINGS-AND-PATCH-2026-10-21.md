## Root causes (both reproduced locally with the 1.1.12 package, evidence G0)
- **A. stale in-flight release row.** The catch-up guard refused whenever ANY release row was `deploying`/`migrating`/`health_checking`. The host still has a row of an old version stuck in such a state (the 1.1.6 deploy that the host process cut off; `reconcileInterruptedDeploys` deliberately leaves a row of another version for manual review). It therefore blocked every catch-up forever. Reproduced: a `1.1.6=deploying` row beside `1.1.12=succeeded` -> HTTP 409 with exactly that message.
- **B. the schema check child process fails on the host and its reason was invisible.** The check runs `node -e <program>` as a child process; on the host it failed with no stderr (consistent with a host process / memory limit killing it, but NOT confirmed: the real exit code / signal was never shown because `execFile`'s message echoes the whole command line and was cut at 400 characters). The gate treats an unverified schema as a blocker.

## Patch (1.1.13)
- Catch-up ignores in-flight rows of a version **older than or equal to** the live build (a deploy of an older version cannot be running next to a newer live build); a **newer** version in flight, or a deploy of this process, still refuses. The ignored rows are logged.
- Child failure is reported as **exit code / signal / timeout / start error / stderr tail** (never the echoed command, never credentials).
- **In-process fallback**: when the child cannot run AND the checked build is the running build (catch-up of the installed release) the same read-only check runs in the application process. A real-Postgres spec runs both implementations against the same databases and requires identical findings. The deploy-time check of a *candidate* build never uses the fallback (it must not mix two builds' classes).

## How 1.1.13 can reach the host - a decision is needed (nothing here is authorized or done)
The host now runs the **1.1.12 engine**, so a 1.1.13 deploy is planned by 1.1.12 code, not 1.1.11. That changes the "R1" premise (deploy with an engine that does not touch Companies):
1. **Deploy 1.1.13 through the Release Center.** With the setting unset the 1.1.12 engine's default is `on`: it takes a verified restore point per lagging Company and migrates them **before the swap**, then verifies. That is the engine's designed path, but it migrates Companies at deploy time (the owner directive restricted this release to deploy-then-explicit-catch-up). Also the 1.1.12 engine runs the same child schema check on the candidate: if it fails on the host as it does for the installed root, the gate **blocks the deploy before any change** (safe stop). Passing it requires `RELEASE_COMPANY_SCHEMA_CHECK=report` in the host environment (an unverified schema then becomes a warning).
2. **Do not deploy; correct the one stale platform row first** (status of the 1.1.6 release row, a platform-database record, not Company data), then use the **1.1.12 catch-up** that is already live. It would migrate both Companies with restore points; because the check cannot run it would report `FAILED` (schema problems: "could not run") although the migrations were applied; verify with the status tool. This is a manual platform-DB edit and needs explicit authorization.
3. Owner diagnostic that is safe and read-only and would tell the real cause of B: on the host, from the application directory run the same node binary with `-e "console.log(1)"` and check the cPanel / CloudLinux resource limits (memory, processes) at the time the Release Center checks the Companies.
