## Addendum 2 — the 1.1.7 upload failed at the pre-swap environment check; host hotfix; correction of an earlier inference (2026-10-10)
- **Host evidence:** release 1.1.7 (uploaded 01:22 Cairo) → `failed` with `ENVIRONMENT_INVALID ... Cannot read properties of undefined (reading 'trim')`. Pre-swap: no migration, active slot untouched (1.1.5 still current), database untouched.
- **Cause (reproduced locally with the exact message):** the installed engine v1.1.5 reads its child process's output with `const { stdout } = await promisify(execFile)(...)`; on this host's runtime `stdout` is `undefined`, so `stdout.trim()` throws and every deploy aborts. The code was new in 1.1.5 and had never run on the host before (1.1.5 was deployed by the 1.1.4 engine). The deploying engine is the INSTALLED one, so a fix inside a new package cannot help the next deploy.
- **Repo fix `6bad4b5`:** the child writes its verdict to a temp file (no dependence on stdout), `runCapture` uses execFile's callback form, and a failure of the check itself is reported as `ENVIRONMENT_CHECK_FAILED` (still fail-closed) instead of claiming the host environment is invalid. `capture-process.spec` (5) + environment-check specs.
- **One-time host hotfix (approved and applied by the operator, 2026-10-10 ~01:59 Cairo):** `patch-envcheck-1.1.5.js` (SHA-256 `d3e694559fe2e38b437cbdf2547e144ac775377ba508976330c37adb4a62d2d7`): dry-run by default, refuses unless the installed file is the known 1.1.5 build (SHA `3cfa3278…`), timestamped backup, `node --check`, auto-restore on failure. Applied result SHA `99c8f1e5af4f1b74bf05903b0d76e1155ee81f41a6cf6a790d4d9259207c380b` — identical to the locally tested result. Backup on host: `dist/foundation/release/release-execution.service.js.bak-20261009225902`. Restart of the application is required for it to load.
- **Consequence for packaging:** the package that was built before this fix (SHA `4e465c26…`) must NOT be deployed: it would replace the hotfixed file with the defective one. It is superseded by a rebuilt 1.1.7 that contains `6bad4b5`.
- **Correction:** earlier in this report series I inferred from the pasted environment (short-looking secrets, no `NODE_ENV` visible) that the host was probably not in production mode, which "weakened" the hypothesis that 1.1.4's new required `DATABASE_CREDENTIAL_ENCRYPTION_KEY` caused the original 503. The operator has now stated **Application mode = Production** (cPanel injects `NODE_ENV=production`; the pasted values were masked by the operator, so their lengths were not real). That inference was wrong: the hypothesis is **not weakened** and stays the leading unconfirmed explanation for the 1.1.4 503.
- **Test-environment note:** a full-regression run on this commit was invalidated (109 suites `ECONNREFUSED 127.0.0.1:5544`) because the isolated PostgreSQL stopped mid-run (host machine interruption); log kept as `full-117b-pgdown-INVALID.log`, run repeated.
