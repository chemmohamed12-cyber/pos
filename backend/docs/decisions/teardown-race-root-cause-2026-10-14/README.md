# Teardown race (`DROP DATABASE … WITH (FORCE)` → 42501 "permission denied to terminate process") — root cause — 2026-10-14

**Status: root cause ESTABLISHED by a direct experiment (mechanism); mitigation `4dc3862` stands; one residual limit stated below.** This replaces "root cause unproven" in the earlier documents.

**Experiment** (`autovacuum_drop_probe.js`, dedicated test cluster 127.0.0.1:5546 — system id 7695619915229547252, PostgreSQL 18.6, `autovacuum = on`, `autovacuum_naptime = 1min`; role `daii_biz_test`, non-superuser; one disposable database `daii_test_biz_t95_avprobe`): a table with 1.5 million rows was updated twice so that autovacuum would pick the database; the script polled `pg_stat_progress_vacuum` (visible to every role) and, **the moment a vacuum worker was reported in that database (pid 6868), issued the same `DROP DATABASE … WITH (FORCE)` the test harness issues.** Result (`result-run1.json`): **error 42501, message "permission denied to terminate process", detail "Only roles with privileges of the role whose process is being terminated or with privileges of the pg_signal_backend role may terminate this process."** — byte-for-byte the failure recorded in the isolation runs. Eight further attempts over about nine seconds failed identically while the worker kept running; the database could be dropped only after the worker had finished (more than a minute later, with the cluster verified clean afterwards: only `postgres`, `template0`, `template1`).

**Mechanism.** `DROP … WITH (FORCE)` terminates the other sessions in the target database, and PostgreSQL refuses when any of them belongs to a role the dropper does not have the privileges of. An autovacuum worker connected to the test database at that instant is such a session (`daii_biz_test` is a non-superuser and not a member of `pg_signal_backend`). The test databases are write-heavy right up to teardown, so autovacuum occasionally selects them; the worker is gone after a short time, which is why the bounded retry recovers it.

**Evidence from the suite:** the two recorded occurrences recovered by the retry (`fixed-asset.company-isolation`, `company-lifecycle-admission.real-pg`) both show the same message and recovery after 750 ms (3 attempts), consistent with a short-lived worker. Those logs did not capture the error detail or the worker, so the link between those two occurrences and this mechanism is by identical message and timing, not by captured proof; the experiment proves the mechanism can produce exactly that failure.

**Residual limit.** The retry window is about 3.75 s (250/500/1000/2000 ms). A database whose vacuum outlasts that window fails teardown — shown with a deliberately large table (3 million dead tuples); ordinary test databases are small and recovered within the window in every observed case. Options if it ever matters (not applied; each is a test-harness or cluster change, not a product change): (a) lengthen the retry window; (b) create disposable tables with `autovacuum_enabled = false`; (c) have the cluster owner run the test cluster with autovacuum off for these databases or grant `daii_biz_test` membership in `pg_signal_backend` (cluster/role change — environment owner's decision). The explicit non-superuser design of the test role is why the product's own guard model should not be loosened for this.

**Disclosure.** The experiment's own cleanup first failed for the same reason (the worker was still running); the database was dropped by retrying until it finished, and the cluster was verified to contain only the three system databases. The script refuses any name other than `daii_test_biz_t9N_*`.
