# Daii — Zero Baseline Cleanup + UUID Repair Runbook

**Read this whole document before running anything.** These are two irreversible, data-mutating
operations on the production database. This session (Claude Code) has no live database access at any
point in this engagement — every step below must be executed by you or a DBA against real
infrastructure. This runbook exists so that execution is mechanical and checkable, not something
requiring you to re-derive the design decisions already made and documented in `HOTFIX_REPORT.md` §5
and the plan behind this delta.

**What this does:** (1) clears test business data while preserving every user/credential/role/
permission exactly as-is (CTO's Zero Baseline correction), (2) repairs primary keys that were
generated by a defective UUID function before it was fixed (Hotfix 5's root cause), cascading the id
change to every table that references it.

**What this does NOT do:** decide for you which `treasury_accounts`, `price_lists`, or
`integration_connectors` rows are real vs. test — see step 3.

## v1.0.3 UPDATE — Controlled Data Repair via the Release Center (RECOMMENDED PATH)

The UUID repair is now a **first-class, logged Release Center capability** — `DataRepairService`
(`src/foundation/release/data-repair.service.ts`) + the `POST /release/data-repairs...` endpoints —
instead of only a hand-run migration. It enforces the exact CTO sequence and freezes every artifact
on a `data_repair_runs` row (audit, mapping, integrity result) as Release Evidence.

**Flow (each step is a separate deliberate call — never one destructive button):**

| Step | Call | What it does |
|---|---|---|
| 1. Backup | `POST /release/backups` | `pg_dump -Fc` + verify (`pg_restore --list`) → a **verified** `BackupRun`. Also writes `storage/backups/manifests/<runId>.json` (version, migration head, artifact SHA256s). |
| 2. Create + Audit | `POST /release/data-repairs` `{ "kind": "uuid_rfc4122" }` | READ-ONLY per-table non-compliant census + sample ids, frozen on the row. |
| 3. Plan | `POST /release/data-repairs/:id/plan` | READ-ONLY reviewable `old → new` id map (new ids via the now-fixed `gen_random_uuid()`). |
| 4. Link backup | `POST /release/data-repairs/:id/link-backup` `{ "backupRunId": "..." }` | Ties the verified pre-repair backup to this repair. **No verified backup → the repair will not run.** |
| 5. Execute | `POST /release/data-repairs/:id/execute` | ONE transaction: FK-defer → rewrite every non-compliant PK + every DB-enforced / soft / hidden / polymorphic / shared-PK reference → `SET CONSTRAINTS ALL IMMEDIATE` → FK-restore. Then integrity verification (FK-orphan sweep, auth/role integrity, zero-remaining re-audit). `completed` only if verification passes. |
| 6. If it fails | `POST /release/backups/:id/restore/preflight` → `POST /release/restores/:id/confirm` | Restore the linked pre-repair backup. |

`ZeroBaselineCleanup` is **NOT** part of this and is not run automatically. The audit result includes
a `zeroBaselineCleanupAdvised` flag; acting on it is a separate manual decision (Steps 2–8 below).

**Rehearse first, always.** `bash tools/data-repair/scratch-rehearsal.sh` stands up an isolated
throwaway Postgres cluster, runs every migration, injects legacy non-compliant ids (reproducing the
prod PG10 state), and drives the whole chain — backup → audit → mapping → repair → integrity →
`@IsUUID()` passes → restore returns the DB to its prior state — with hard assertions. Evidence lands
in `tools/data-repair/rehearsal-evidence/`. This rehearsal **caught a real latent bug** in the
original repair (SQLSTATE 55006, `cannot ALTER TABLE ... because it has pending trigger events` — the
`SET CONSTRAINTS ALL IMMEDIATE` before restoring constraints, now in `uuid-repair.core.ts`), which
would otherwise have failed the production run.

**Evidence retention (CTO):** keep the pre-repair backup, the `data_repair_runs` row (mapping +
results), and the audit output. Do NOT delete them right after a successful repair.

The migration path (below, Steps 1–8) is still supported — the deferred
`1755852700000-RepairNonCompliantUuids.ts` now just calls the same shared `runUuidRfc4122Repair`
core. Use it only if you specifically want a migration rather than the tracked capability.

## Step 0 — Prerequisites

- SSH/DB access to the real host (this session has never had this).
- `pg_dump`/`pg_restore`/`psql` available (already required by the project's own
  `PRODUCTION_DEPLOYMENT_GUIDE.md`).
- A scratch Postgres instance/database to restore into (does not need to be on the same host — any
  reachable Postgres 10+ works, matching production's actual version, 10.23).
- This delta's `backend/` deployed somewhere you can point at either the scratch DB or production via
  environment variables, to run the 578-test suite and boot the app against each.

## Step 1 — Backup (CTO requirement #1)

```bash
PGPASSWORD=<password> pg_dump -h <host> -p 5432 -U daii -Fc -f daii_pre_repair_$(date +%Y-%m-%d).dump daii_dev
```

Keep this file. It is the real rollback path for both migrations below — neither has a working
`down()` that undoes the data change (deliberate; see each migration's own doc comment).

## Step 2 — Restore into a scratch database

```bash
createdb -h <host> -p 5432 -U daii daii_scratch_repair_test
PGPASSWORD=<password> pg_restore -h <host> -p 5432 -U daii -d daii_scratch_repair_test --no-owner daii_pre_repair_*.dump
```

**Everything from here through Step 8 runs against `daii_scratch_repair_test`, never against the real
`daii_dev`/production database, until Step 9 explicitly says otherwise.**

## Step 3 — Run the diagnostics, review, and confirm the ambiguous items

```bash
cd backend
psql -h <host> -U daii -d daii_scratch_repair_test -f tools/data-repair/uuid-audit.sql
psql -h <host> -U daii -d daii_scratch_repair_test -f tools/data-repair/zero-baseline-deletion-report.sql
```

Review the output. In particular, resolve the 5 items `zero-baseline-deletion-report.sql` §3 flags as
needing your judgment (treasury accounts, price lists, integration connectors, audit-history
retention, non-MAIN-WH warehouses currently holding stock). If any of them need the migration's
behavior adjusted (e.g. you decide a specific `treasury_accounts` row IS test data and should be
deleted), either delete that specific row by hand after Step 4 completes, or tell me and I'll adjust
`ZeroBaselineCleanup1755852600000.ts` before you re-run this on the real database.

## Step 4 — Run the Zero Baseline cleanup (on the scratch DB)

```bash
DB_HOST=<scratch-host> DB_PORT=5432 DB_USER=daii DB_NAME=daii_scratch_repair_test DB_PASSWORD=<password> \
  npm run migration:run
```

This applies every pending migration in order, including `ZeroBaselineCleanup1755852600000` — watch
the console output for its `RAISE NOTICE` lines (one per table, showing exactly how many rows were
deleted) and compare them against the counts you reviewed in Step 3.

**If this fails partway**: the whole migration runs inside TypeORM's own migration-batch transaction,
so a failure rolls back completely — nothing is left half-deleted. Fix the issue, then re-run.

## Step 5 — Run the UUID repair (on the scratch DB, same command)

The same `npm run migration:run` invocation also applies `RepairNonCompliantUuids1755852700000`
(pending migrations run in one invocation, in order) — if you ran Step 4 and 5 as one `migration:run`
call, this already happened. Watch for its `RAISE NOTICE` lines (`old_id -> new_id` per repaired row,
plus a final total count).

## Step 6 — Verify (on the scratch DB)

```bash
psql -h <host> -U daii -d daii_scratch_repair_test -f tools/data-repair/uuid-audit.sql
# every non_compliant_rows column should now read 0
psql -h <host> -U daii -d daii_scratch_repair_test -f tools/data-repair/post-repair-verification.sql
```

Every check in `post-repair-verification.sql` must come back clean (see the FAIL conditions noted
inline in that file) before proceeding.

## Step 7 — Full regression + critical E2E (against the scratch DB)

```bash
cd backend
npm test  # expect 578/578 — this suite is DB-independent/mocked, but re-run for completeness
DB_HOST=<scratch-host> DB_PORT=5432 DB_USER=daii DB_NAME=daii_scratch_repair_test DB_PASSWORD=<password> \
  NODE_ENV=production PORT=3500 JWT_ACCESS_SECRET=<32+chars> JWT_REFRESH_SECRET=<32+chars> \
  INTEGRATION_ENCRYPTION_KEY=<32+chars> node dist/main.js
```

With the app running against the scratch DB, walk through the CTO's own list live in a browser:
customers, accounts, orders, warehouses, financial transactions (deposit approval, cash-in — the exact
two flows from Hotfix 5), inventory, shipments, returns, audit. At minimum: log in as one of the
preserved users, confirm their role/permissions still work, create one fresh customer/product/order to
confirm the golden path still functions from a clean baseline, and re-run the Hotfix 5 deposit-approval
flow to confirm no `must be a UUID` error occurs on a freshly-created (now-compliant) treasury account.

## Step 8 — Only if Step 6 and 7 are fully clean, repeat on real production

1. Take a **fresh** backup (repeat Step 1 — do not reuse the one from before the scratch-DB rehearsal,
   production may have changed since).
2. Run `npm run migration:run` against the real production database.
3. Run Step 6's verification queries against production.
4. Run Step 7's browser walkthrough against production (not just the scratch copy).

## Step 9 — Sign-off

Only once Step 8 is fully clean is this operation done. If anything in Step 6/7 fails on the scratch
copy, **do not proceed to Step 8** — fix the issue (in the migration files, or by adjusting the
confirmed-ambiguous-item list from Step 3), and restart from Step 2 with a fresh scratch restore.

## Rollback (either environment)

Neither migration has a working `down()` — restore the pre-operation `pg_dump` backup from Step 1 (or
Step 8.1 for the production run) instead:

```bash
dropdb -h <host> -U daii daii_dev
createdb -h <host> -U daii daii_dev
PGPASSWORD=<password> pg_restore -h <host> -U daii -d daii_dev --no-owner daii_pre_repair_*.dump
```
