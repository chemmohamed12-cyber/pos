# XNEXUS RMS (Step 30) — Kernel Capability Audit for Daii Platform

Source: `xnexus-rms-step30` zip extract, commit `bae026f` (Steps 1–30). Cross-referenced against `XNEXUS_RMS_Step30_FINAL_Implementation_Report.md` and `Daii_Platform_Architecture_Blueprint_V1.md` §5–9, 32, 33, 41.

## 1. What this codebase is

XNEXUS RMS is a **NestJS 10 / TypeScript 5.5 monorepo** implementing what it calls a "Platform Foundation" — a set of 20 kernel/* infrastructure modules, all live-wired into `apps/api/src/app.module.ts`, plus a `packages/platform-sdk` facade layer that Business Modules are meant to consume instead of importing kernel internals directly (ADR-006, mechanically enforced via an ESLint `no-restricted-imports` rule that specifically targets `apps/api/src/modules/**` importing `**/kernel/**`). Ten Business Module directories exist under `apps/api/src/modules/*` (`branch, config, customers, iam, inventory, kds, reporting, sales-pos, suppliers, tables`) but are **verified-empty skeletons** — each has exactly `domain/`, `application/`, `infrastructure/`, `interface/` folders containing only a `.gitkeep`, generated mechanically by `tools/generators/generate-module.js` and confirmed by `tools/validation/validate-structure.js`. Zero business logic exists anywhere in `modules/*`.

Governance discipline is unusually high and worth noting on its own: every kernel service carries an explicit doc-comment banner reading **"MINIMUM-FOUNDATION STUB"**, naming exactly what real-world requirement (RMS-doc section, ADR number) it does *not* implement, and why. The project runs a numbered "Build Order" (Steps 1–30) with per-step Implementation Reports, tracks architecture decisions as ADRs (up to ADR-035), and the Step 30 report itself discloses two unresolved judgment calls (a module-list source conflict, and an ambiguous "registered at boot" acceptance criterion) rather than silently picking an answer. This is a real, load-bearing engineering culture, not just comment decoration — see §5 below.

Architecturally, this is **not a web B2B commerce backend** — it is the server-side kernel for a POS/restaurant terminal system, explicitly repositioned by ADR-035 (July 2026) from "Restaurant Management System" to a configurable "F&B Hospitality Platform" (cafés, bakeries, cloud kitchens, food courts — still all point-of-sale/food-service, not B2B distribution). Its own Business Module list (`sales-pos`, `kds` — kitchen display system, `tables`, `branch`, `inventory`, `customers`, `suppliers`, `reporting`, `config`, `iam`) is confirmed by direct inspection to be POS/restaurant-shaped and does **not** map onto Daii's blueprint domain list (Commerce/CRM/Sales/Orders/Warehouse/Logistics — Sections 8–29 of the blueprint). Roughly half the kernel (`desktop-runtime`, `hardware`, `device-identity`, `local-database`, `local-event-store`, `local-runtime`, `sync-queue`, `update-framework`, `recovery-foundation`, `platform-protection`) exists to support an **offline-capable desktop/POS terminal** — hardware peripherals (cash drawer, receipt printer, barcode scanner), local SQLite-style storage with cloud sync queues, machine-bound license enforcement, and self-update — none of which has any analog in a hosted web/mobile B2B platform. Overall relevance to Daii: **low on code reuse, non-trivial on architectural pattern (kernel/SDK/business-module boundary discipline) and governance-process reuse.**

## 3. Top candidates for extraction

**Audit Engine (`kernel/audit`)** — The strongest single asset. The hash-chain design (each record's hash commits to its own content + the prior record's hash, with a fixed genesis hash so chain-splicing at position 0 is also detectable) is algorithmically sound, small, dependency-free (just Node's built-in `crypto`), and framework-agnostic — it is plain TypeScript using `createHash('sha256')`, not a NestJS-specific construct. It needs a persistence backend (currently in-memory only) and a real actor/tenant source, but the verification algorithm itself could be ported to any Node/TS backend, NestJS or not, with minimal adaptation. Extraction risk: low — small, self-contained, one spec file exists as a starting regression test.

**Event Bus (`kernel/event-bus`)** — The *interface* (`EventBusService.publish/subscribe`, and the discipline of "no module may import a broker SDK directly") is a clean match for blueprint §32's durable-business-events requirement. The shipped implementation is explicitly an in-memory placeholder ("not RabbitMQ... no broker reachable from this environment") with one genuinely real behavior (durable local write before dispatch). Extraction risk: medium — the contract is reusable, but a production implementation (against whatever broker/queue Daii selects) must be written from scratch; nothing about the current implementation survives as-is.

**Authentication/Authorization/Tenant-Context (`kernel/authentication`, `kernel/authorization`, `kernel/tenant-context`)** — Grouped together because they share one finding: **every one is explicitly self-labeled "MINIMUM-FOUNDATION STUB"** in its own source comments, and none does what its name implies. Authentication trusts unsigned `x-user-id`/`x-user-roles` headers with no JWT/session verification at all; Authorization is a single `roles.includes(role)` check with no permission/scope model; Tenant-Context is an AsyncLocalStorage variable with no real Tenant Configuration Hierarchy behind it. The *pattern* (AsyncLocalStorage-based request-scoped context, propagated via middleware) is worth reusing as an implementation technique regardless of stack. The *code* is not production auth and must not be mistaken for it — this is the single most important risk-flag in this audit given Daii blueprint §33's explicit requirement that "a user must be technically unable to retrieve unauthorized customers, orders, inventory, shipments, or APIs" server-side.

**Configuration / Feature Flags (`kernel/configuration`, `kernel/feature-flags`)** — Configuration is a bare `process.env` wrapper, not extractable as an engine. Feature Flags has real (non-stub) resolution-order logic (tenant-override → global-default → built-in-default) worth reusing as a pattern for Daii's own Configuration capability, but its persistence layer and its coupling to this project's specific license-plan model would need to be rebuilt.

**Generator/Validator tooling (`tools/generators/generate-module.js`, `tools/validation/validate-structure.js`)** — The most stack-neutral asset in the entire codebase: both are plain Node.js scripts using only `fs`/`path`, with zero NestJS or even TypeScript dependency (they're plain `.js`, not `.ts`). They could be copied into Daii's own tooling with only the layer-name list and root-path constants changed, independent of whatever backend stack Daii ultimately picks. This is a **process-discipline reuse**, not a code-domain reuse, and is the safest, lowest-risk extraction in this whole audit.

**Key open architecture question (stack compatibility)**: This entire codebase — kernel, SDK, tooling's lint-rule enforcement — is NestJS/TypeScript. Per the discovery brief, the other two Daii source repositories (`baseline/` and `xnexus-website/`) are described as plain Express/JS. If Daii standardizes on the NestJS/TS stack, this kernel's *code* (not just its patterns) becomes meaningfully reusable as a starting skeleton for Authentication/Authorization/Audit/Event-Bus scaffolding. If Daii standardizes on plain Express/JS to match the other two sources instead, **none of this code ports directly** — every extraction listed above becomes a "re-implement the pattern in a different stack" exercise, not a copy/adapt exercise. This decision should be made explicitly and early (Stage 1 — Foundation Extraction, per blueprint §45), since it changes nearly every classification in this table from "C — Extract" to effectively "D — Rebuild, same idea, different stack."

## 4. Reject / Not applicable

- **`kernel/desktop-runtime`** — boots/orchestrates a local POS terminal process and its online/offline runtime-mode state machine; no web/mobile B2B platform equivalent.
- **`kernel/hardware`** — cash-drawer, receipt-printer, barcode-scanner, customer-display provider abstractions; literal POS peripheral drivers, not applicable to Daii.
- **`kernel/device-identity`** — generates machine/installation fingerprints solely to support per-install software licensing; Daii is not sold as installed software.
- **`kernel/local-database`** — offline local datastore for a terminal that must function without connectivity; Daii has no stated offline-first requirement.
- **`kernel/local-event-store`** — durable local write-before-broadcast log, solving the "sync when reconnected" problem that only exists for offline-first clients.
- **`kernel/local-runtime`** — tracks which node (local vs. cloud) has decision authority when offline; irrelevant absent an offline mode.
- **`kernel/sync-queue`** — inbox/outbox reconciliation between a disconnected terminal and the cloud; no analog for an always-connected backend.
- **`kernel/update-framework`** — self-update mechanics (version compare, update catalog, installer) for a distributed desktop binary; Daii is centrally deployed.
- **`kernel/recovery-foundation`** (Safe Mode portion) — degraded-boot state machine specific to a local terminal that must keep operating without its usual dependencies; the snapshot/restore idea is generically useful but this implementation is written for local-terminal recovery.
- **`kernel/license-context`** and **`kernel/platform-protection`**'s license-artifact logic — per-installation software licensing/entitlement/anti-tamper machinery; Daii is not licensed-and-installed software (the generic HMAC sign/verify utility inside `platform-protection` is the one salvageable piece, noted in §3).
- **`apps/api/src/modules/branch`, `sales-pos`, `kds`, `tables`** — restaurant/POS-specific Business Module names with zero implementation to extract anyway; even the *concept* of these four doesn't map to Daii's domain list.
- **`apps/api/src/modules/config`, `customers`, `iam`, `inventory`, `reporting`, `suppliers`** — also empty skeletons; the *names* loosely echo Daii's domain vocabulary (Customers, Suppliers, Inventory, IAM) but contain no logic whatsoever to evaluate — note them only as a reminder that name overlap alone is not evidence of reusable content.

## 5. Flagged risk / process observation

Independent of code reuse, this project's **governance culture is itself a transferable asset**. Three concrete behaviors worth noting for Daii's own process, distinct from anything in the code:

1. **Every stub is labeled as a stub, in the code itself**, with a specific pointer to what real requirement it does not satisfy (e.g., "real JWT/session security is Step 10's undelivered scope; real RBAC/ABAC is Step 11's"). This means a future engineer opening `authorization.service.ts` cannot mistake it for production authorization — the comment forces the correction. Blueprint §41 principle 2 ("No silent refactoring") and the Required Capability Audit template (§6) both implicitly want this same property audited into every extracted engine; RMS demonstrates it can be done at the source-comment level, not just in a separate document.
2. **Disclosed discrepancies over silent resolution** — the Step 30 report's §2 (module-list source conflict between three governance documents) and §3 (ambiguous "registered at boot" criterion) are both surfaced explicitly with the reasoning for the choice made, rather than picked quietly. This is precisely the posture Daii blueprint §6 demands ("No silent copying is allowed") and §41 requires ("No silent refactoring").
3. **A frozen, validated repository-shape convention, mechanically checked** (`validate:structure`, ESLint boundary rule) rather than left to code review discipline alone — worth adopting as a CI gate for Daii's own Foundation/Business-Module split, regardless of whether any RMS code itself is reused.

This is a process pattern to imitate, not a code dependency to import — it does not change any capability's A–E classification above, but it is worth carrying forward as an explicit recommendation for how Daii's own Stage 1+ work should be documented and reviewed.
