# Stage 0 Discovery Audit — QR Platform (`xnexus-website/`)
## Source Codebase Assessment for Daii Platform

---

## 1. What This Codebase Actually Is

Despite the folder name `xnexus-website` and its `package.json` self-description ("independent Marketing Platform, Website & Platform Separation, Stage 2"), this codebase has organically grown far past a marketing site into a **multi-tenant, single-Node-process, JSON-file-persisted SaaS platform** combining: (1) a QR-menu / restaurant-ordering CMS ("QR Platform" proper — projects, products, studios, WhatsApp ordering), (2) a **Consumer Discovery network** (Places, Discovery feed, guest-first mobile app), (3) a fully-built **External Business Delivery Dispatch domain** (Business Customer → Delivery Request → Eligibility → Dispatch → Offer → Assignment → Execution → GPS Tracking), and (4) a **Package/Permission/Limit entitlement engine** governing what a tenant's CMS can see and how much it can use. Three native mobile app shells (`driver-apk`, `consumer-apk`, `business-delivery-apk`, all thin Capacitor wrappers around one `www/index.html` each) sit alongside the server. The server entrypoint (`server/server.js`, 317KB, ~340 routes) and CMS (`cms/cms.js`, 674KB) are large single files, but the business logic itself is well-decomposed into ~45 `server/engines/*.js` engines and ~45 `server/repositories/*.js` repositories, each with a one-owner-per-file discipline.

**Maturity**: this is, by a wide margin, the most production-hardened and best-documented of the source candidates. Every non-trivial feature ships with a paired stack of short, high-signal Markdown reports — Architecture, Security, Concurrency, Audit Trail, Live-HTTP Verification, Regression, Data Safety, Changed-Files, Migration Notes — written *as engineering evidence*, not marketing copy (e.g. "24/24 direct HTTP checks passed... real running server, real tokens"). The Dispatch/Delivery domain (Phases C, D, E, F) in particular reads like a genuine CTO-directive-driven, audited build: every design decision (why offers are a separate entity from assignments, why capacity checks are re-verified at accept-time, why GPS location uses an in-memory cache instead of the codebase's usual synchronous-file-write pattern) is explained and justified in-line, and cross-checked against its own prior phases by file-mtime diffing to prove nothing else was silently touched.

**Overall relevance to Daii**: **highest of the three sources**, exactly as expected. The Business Delivery Dispatch domain (Sections 25–28 of the blueprint: Shipment, Waybill, Delivery, Tracking) maps almost one-to-one onto a Fulfillment/Dispatch subsystem; the Egypt Geography Master (Phase F) is a direct, ready-to-extract asset for Daii's Egypt-only warehouse/delivery scoping; the Permission Engine + Limit Engine pairing is exactly the "deny-by-default hierarchical node, fail-open numeric quota" pattern Section 7 asks for (though it is *package/tenant-scoped*, not *per-user role-scoped* — see the classification notes below, this is a real architectural gap relative to what Daii's Sales hierarchy needs); and the i18n architecture (Section 34–40) is a proven, working Arabic-default/English-toggle/RTL-mirroring pattern, though it is UI-chrome-vocabulary only, not a canonical-code-to-localized-label business Terminology Registry.

**The single biggest structural caveat for extraction**: the entire platform's persistence layer is `fs.readFileSync`/`writeFileSync` (atomic via tmp-file-rename) JSON files, one file per entity type, no database. Several of the codebase's most celebrated correctness guarantees (the Offer-Accept race-condition atomicity, in particular) are explicitly and self-admittedly **contingent on this synchronous-file-I/O property** — the Phase C reports flag, in their own words, that if persistence ever becomes async (a real DB), "this entire file's atomicity claim must be re-audited." Daii, being a real ERP-grade multi-warehouse system, will need a real transactional database from day one, so this dependency cannot be extracted as-is — the *state-machine and ownership-check logic* is reusable, the *concurrency-safety mechanism* is not and must be rebuilt on real DB transactions/row-locks.

## 3. Top Candidates for Extraction

**1. Permission Engine + Limit Engine (`server/permissions/*.js`, `server/engines/permission-engine.js`, `server/engines/limit-engine.js`)** — The hierarchical deny-by-default node resolution (with its explicit ancestor-walk inheritance, 404-not-403 anti-enumeration for hidden nodes, and "fail-closed on permissions but fail-open on limits" dichotomy) is a mature, well-reasoned design and the closest thing in any source repo to blueprint §7's Permission/Limit/Scope Engine ask. What must be stripped/rebuilt: the resolution currently operates at *Website/tenant* granularity only (one permission set per site, keyed off a Package→Profile chain) with a single super-admin bypass — it has no concept of per-user roles (Sales Rep / Supervisor / Manager / Warehouse Worker) or per-user *scope* (which customers/warehouses this specific user may see), which is exactly what Daii's Sales hierarchy (§11) and Sales Rep customer-scope (§22, §33) require. Extraction risk: low for the algorithm, medium for the redesign effort to add a per-user dimension on top of the existing per-tenant dimension. Maps to: Daii's **Permission Engine + Scope Engine** (§7), and directly informs the server-side-only enforcement mandate of §33.

**2. Delivery Dispatch domain (`server/engines/delivery-domain/*.js` + matching repositories)** — This is the single highest-value asset in the codebase. The Request → Eligibility → Availability filter → Capacity filter → Offer (separate entity, PENDING/ACCEPTED/REJECTED/EXPIRED/CANCELLED) → Assignment (separate entity again) → Execution state machine (ASSIGNED→STARTED→PICKED_UP→IN_TRANSIT→DELIVERED/FAILED/CANCELLED, with a full `statusHistory[]` array and an explicit actor-based authorization matrix) is architecturally almost a direct match for blueprint §23 Fulfillment Engine and §25–26 Shipment/Waybill. What's QR/restaurant-coupled: essentially nothing structural — this domain was already built deliberately independent of the QR Domain (verified by its own phase reports' "zero QR dependency" checks). What must be rebuilt: the atomicity guarantee for the Offer-Accept race condition is explicitly, self-documentedly contingent on the codebase's synchronous JSON-file persistence — this must become a real DB transaction/row-lock in Daii, and every phase report that proves concurrency-safety says so itself. Extraction risk: low for the domain model and state machines, medium for the concurrency rebuild. Maps directly to: `delivery-offer-repository.js`/`delivery-assignment-repository.js` → Daii's **Fulfillment Engine pick/dispatch/assign flow** and **Shipment lifecycle** (§25); `delivery-execution-engine.js`'s statusHistory → Daii's **Waybill tracking events** (§26).

**3. Geography Engine + Egypt Geography Master Data (`server/engines/geography-engine.js`, `server/repositories/geography-repository.js`, Phase F reports)** — Near-direct reuse candidate. The Governorate→City/Markaz→District→Area/Zone→Street hierarchy, sourced from official UN OCHA/HDX P-codes with stable opaque IDs (never a bare display name used as a key — already matching blueprint §37's canonical-code rule), plus the honest nearest-centroid GPS resolution with confidence tiers, is exactly what Daii needs for Customer addresses, Warehouse locations, and Delivery-zone scoping — and it's the *same country*. What's coupled: nothing structurally QR-specific; this was built as an independent Master Data module from the start. What must change: persistence (JSON file → real DB table), and the seed data itself should be re-validated/re-downloaded from the primary HDX source rather than assumed. Extraction risk: low. Maps to: Daii's Customer/Warehouse address model and §25 Shipment destination resolution.

**4. i18n / Arabic-first architecture (`cms/cms-i18n.js`, `LANGUAGE_I18N_DOCUMENTATION.md`)** — A proven, working pattern: Arabic-default-on-first-launch (never derived from device locale), `xnexus_lang` persisted choice, flat `TRANSLATIONS[lang][key]` dictionary with English-fallback-never-blank, `dir="rtl"/"ltr"` toggling that "just works" because every layout uses flexbox row/space-between rather than hardcoded left/right. This is a solid reference for blueprint §39 RTL/LTR mechanics and the general default-to-Arabic discipline of §34. What's missing relative to what Daii needs: this is a *client-side UI-chrome vocabulary* dictionary (button labels, module names, "Save"/"Cancel"), not a server-owned canonical-code-to-localized-label **Terminology Registry** for business domain vocabulary (order statuses, warehouse terms) as blueprint §36 specifies — Daii needs the registry to be server-side and API-exposed so canonical codes (e.g. `PENDING_REVIEW`) never leak as literal Arabic/English strings into business logic, which this codebase's own docs explicitly flag as an intentionally *unsolved* piece even for raw status enums ("localizing them would require maintaining a second, drift-prone mapping never requested"). Extraction risk: low for the RTL/mirroring mechanics, but the Terminology Registry itself must be built new, informed by this pattern rather than lifted from it.

**5. QR-Package entitlement model (`server/engines/qr-package-engine.js`, `QR-PACKAGE-03-ENTITLEMENT-LIMIT-MODEL.md`)** — A clean two-tier extension of the site-level Limit/Permission Engine pattern down to a per-object (per-QR-Project) granularity, with the identical fail-open-by-absence philosophy and idempotent, dangling-reference-safe resolution. Lower priority than items 1–3 for Daii V1 (Daii's blueprint doesn't call for a subscription/package system in V1), but directly relevant if/when Daii adds per-branch or per-customer feature tiers, or a partner/reseller model in a later phase. Extraction risk: low, but currently not urgent — flag as a Phase-2-adjacent asset rather than a V1 extraction target.

## 5. Security Observations (Blueprint §33)

**Overall: yes, this platform is a strong reference for server-side-enforced authorization.** Every phase report's own Security section independently verifies authorization over **real HTTP against a real running server with real tokens**, not just unit-level assertions — e.g. Phase C's "24/24 direct HTTP checks passed... isolated scratch data," and every cross-actor-access test (Driver A → Driver B's Offer/Assignment/Availability, Business Customer A → Customer B's Request) is proven to return **404, never 403**, which is a deliberate anti-enumeration discipline consistently applied across every domain — a non-owner never even learns the resource exists. Forged IDs in request bodies are consistently ignored or rejected; ownership is always re-derived from the authenticated identity server-side, never trusted from a client-supplied parameter (explicitly proven, e.g., for `GET /api/driver/assignment` and for the GPS-location Assignment-binding check). The Authorization Matrix reports (Phase D-02) go further than most codebases by mechanically confirming that forbidden actions **don't just get rejected at runtime — the code path structurally doesn't exist** (`typeof execEngine.cancelByDriver === 'undefined'`), which is a stronger guarantee than a runtime check that happens to currently reject. The client-side permission cache (`cms/permission-gate.js`) explicitly documents itself as UX-only and not a security boundary, directly matching blueprint §33's "never rely on hidden UI buttons" principle.

**The one documented incident — `HOTFIX-ENGINEERING-INCIDENT-REPORT.md`** — is not a security/authorization breach; it's a **client-side reliability defect**, worth understanding as risk knowledge for Daii regardless. Summary: a customer's "Send Order" button on the public QR menu would occasionally silently do nothing (recoverable only by a page refresh), traced to two real, confirmed root causes in `public-site/js/catalog-core.js`: (1) the Send Order click handler had no `.catch()`/`try-catch` anywhere in its promise chain and no duplicate-submission guard, so a rapid double-click or an unexpected promise rejection could silently fail or double-fire; (2) the product-detail `fetch()` call had no error handling, and because `fetch()` does not reject on a non-2xx HTTP status, a legitimate server-side 404 response was silently swallowed with zero user feedback. The fix was scoped as a narrow, defensive hotfix (duplicate-submission guard, synchronous "Sending…" state, `.catch()` handlers, visible retryable error toast) with explicit, audited discipline: **no changes to any business logic**, proven via a new regression test that fails against the pre-fix code and passes against the fix. **Relevance to Daii**: this is a directly applicable lesson for Daii's Sales Order submission flow (§13) and any driver/warehouse mobile-app action button (§12, §24) — every state-changing client action needs (a) a duplicate-submission guard, (b) explicit loading/pending UI state, (c) a `.catch()`/error path with visible user feedback, and (d) awareness that `fetch()` never rejects on 4xx/5xx by default. This is a reliability/UX-defect class, not an authorization gap, but it's exactly the kind of silent-failure risk a multi-step approval workflow (Draft→Submitted→Supervisor→Manager→Deposit→Release) is especially vulnerable to if any one of its state transitions has the same gap.

**One structural risk worth flagging explicitly for Daii, not called out as an "incident" in the source docs but visible from direct code review**: the homegrown HMAC-token authentication is reimplemented near-identically four separate times (CMS, Driver, Consumer, Business Customer), each with its own `process.env`-sourced secret defaulting to a hardcoded `'dev-only-...-do-not-use-in-production'` string when the env var is unset. This is a real production-deployment risk class (a misconfigured deployment silently running with a well-known dev secret) that Daii's Foundation Authentication (§7) should design out from the start via a single, centrally-configured auth service with a startup-time hard failure on missing/default secrets, rather than a per-domain fallback default.

## 6. Arabic-First i18n Architecture Note (Blueprint §34–40)

The codebase separates a **UI-chrome vocabulary layer** cleanly from **business logic**, but does *not* yet implement a true canonical-code-to-localized-label Terminology Registry at the business-data level — this is an important distinction for Daii to get right where this source got it partially right.

What works well and is a good reference: (1) Arabic is the enforced default on first launch, explicitly *never* derived from `navigator.language`/device locale — this directly matches blueprint §34's "Arabic is the default operational language" mandate and avoids the common bug of a Cairo user with an English-locale phone seeing an English app by accident. (2) The language choice, once made, persists via a single `localStorage` key shared consistently across the public site, the CMS, and (with the same key name, deliberately, even though storage isn't literally shared across separate mobile app installs) the Driver/Consumer APKs. (3) RTL/LTR is a single `dir` attribute toggle that "just works" across the whole UI because every layout is built with flexbox row/space-between rather than hardcoded `left`/`right` — this is the correct architectural default blueprint §39 asks for ("do not build the interface as LTR-only and retrofit RTL later"), and this codebase already proves the pattern works end-to-end including direction-aware (not merely mirrored) icon glyphs. (4) `t(key)` always falls back to the English string, never a blank or a raw key shown to a user — a good "never leak an internal identifier" discipline, reinforced by a real historical bug the codebase's own CMS Sidebar Reorganization report caught (`module.ai-management` literally appearing in the UI before its translation key was added).

What is explicitly **not** present, and is exactly what blueprint §36–38 requires Daii to build fresh: the codebase's own i18n documentation is candid that **raw server-owned status enum values (e.g. `OPEN_FOR_OFFERS`, `ASSIGNED`, `PICKED_UP`) are deliberately left untranslated and shown verbatim** on the Driver app, explicitly because "localizing them would require maintaining a second, drift-prone mapping never requested by this Directive." This is precisely the anti-pattern blueprint §37 warns against avoiding in the other direction (never storing the localized string as the canonical value) — but this codebase's solution is to simply *not* localize those values at all rather than build a proper registry that maps `code → {ar, en}` labels the way blueprint §36's worked example (`pending_review → ar: بانتظار المراجعة, en: Pending Review`) specifies. For Daii, this means: reuse the RTL/LTR mechanics, the default-to-Arabic-never-locale-derived rule, and the never-blank-fallback discipline from this codebase directly, but the actual Terminology Registry — a server-side, API-exposed, canonical-code-keyed table separating machine values from professionally-authored Arabic and English business labels — must be designed and built new; it is a real gap even in this, the most mature of the three source platforms.
