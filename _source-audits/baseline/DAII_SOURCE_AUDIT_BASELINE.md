# Stage 0 Capability Audit — `baseline/` (XNEXUS Wireless Hospitality Calling System)

Source: `D:\CLAUDE-CODE\XNEXUS-WORKSPACE\baseline\`
Scope of this document: `baseline/server/*` only (engines, repositories, kernel, endpoint files), cross-referenced with `baseline/engineering/INDEX.md` and `baseline/docs/architecture/`.

---

## 1. What this codebase actually is

`baseline` (`package.json` name `"xnexus"`, description *"XNEXUS Wireless Hospitality Calling System"*) is a monolithic Node/Express server (`server/server.js`, ~172KB, one process, `app.use(express.json())` + hand-rolled JWT auth) backing a **guest-paging / device-manufacturing / warranty ERP** for a hospitality-hardware business — not a restaurant RMS and not an e-commerce/B2B commerce platform. Its real domains are: Purchase Requests → Sales Orders → Warranty issuance/certificates → Asset (serialized device) tracking → Manufacturing/BOM/Assembly/Quality → Demo Request/Deployment (device loaners) → a marketing CMS (Content/Showcase/Placements) for the public site → a large "Planning Center" (generic task/visit planning with a configurable approval workflow) → a "Platform AI" assistant layer → Backup/Restore/Sync infrastructure. Persistence is **flat JSON files under `data/`**, accessed through a small but consistent Repository abstraction (`server/repositories/base-repository.js` + ~35 subclasses), never a real database.

Architecturally the codebase is unusually well-documented and disciplined for what it is: every Engine follows the same explicit "Engine Contract" (Validation → Authorization → Business Rules → Repository → Events → Audit → Response), every extraction is accompanied by a written rationale, and a large `engineering/INDEX.md`/`docs/architecture/` trail records design decisions, ADRs, and even root-cause analyses of production incidents. That discipline is itself a reusable *process* asset. However, the **business content** is overwhelmingly hospitality/manufacturing-specific (serialized "Assets" = physical calling devices, Manufacturing/BOM/Assembly/Quality/System-packaging, Warranty certificate PDF generation, Demo device loaner logistics), and the **permission model is not a real RBAC engine** — it is dozens of independently hard-coded `['role-a','role-b'].indexOf(user.roleId)` arrays duplicated per Engine ("duplication, not sharing" is stated explicitly as the deliberate convention in multiple file headers).

Overall relevance to Daii: **low-to-moderate as code, moderate-to-high as pattern/architecture reference.** The single most valuable concrete asset is the generic, stateless, domain-agnostic **approval workflow state machine** (`process-engine.js`) plus a genuinely clean, warehouse-agnostic **inventory ledger** (`inventory-ledger-engine.js`). Everything serialized-asset/manufacturing-specific (the majority of the "Warehouse" surface: `asset-engine.js`, `manufacturing-engine.js`, `bom-engine.js`, `assembly-engine.js`, `quality-engine.js`, `finished-goods-warehouse-engine.js`, `raw-material-engine.js`) is quantity-blind (one record = one physical serial number) and does not match Daii's SKU/quantity-based, multi-warehouse commerce model — those are Reject or, at best, "extract the state-machine pattern only."

## 3. Top candidates for extraction (Daii V1)

**1. `engines/process-engine.js` — Approval Workflow Engine (Classification A/B).**
This is the standout find of the entire audit. It is a stateless, fully generic state machine that knows only `(state, action, actor, excludedActor)` — no knowledge of "plans," "orders," or any business noun. Default states (`draft → pending_review → approved | pending_resubmission → pending_final_approval → ...`) map almost directly onto blueprint §14's Draft→Submitted→Supervisor Review→Manager Approval flow. Extraction risk is low: it has no repository, no persistence, and is already proven as a reused component inside this same codebase (Planning Center and Execution Runtime both build on it). The only work needed is wiring Daii's own state names/actions and persistence around it.

**2. `engines/inventory-ledger-engine.js` — Inventory Ledger (Classification B).**
Matches blueprint §17-18 (transaction-based inventory, stock always derived from movements, never a mutable quantity) almost exactly, and it is genuinely domain-neutral — it is explicitly designed to be partitioned by an `inventoryType` string with zero business opinion baked in. What's missing for Daii: a warehouse/location dimension (today it only has `stockRefId`, effectively per-SKU, no per-warehouse split), and Daii's richer stock-state vocabulary (reserved/allocated/picked/packed/in-transit/delivered/returned vs. this engine's simple receipt/consumption/transfer/adjustment). Extraction risk is low-medium: the core ledger math (`getStockLevel`, `getStockSummary`) is solid and battle-tested (used by 3 warehouse consumers), but every *consumer* (`finished-goods-warehouse-engine.js`, `raw-material-engine.js`) is manufacturing-coupled and must be rebuilt from scratch for Daii's SKU/qty warehouse model — do not extract the consumers, only the ledger core.

**3. `engines/work-engine.js` / `engines/execution-engine.js` — Generic Task/Execution Lifecycle (Classification B).**
Two complementary generic engines: `work-engine.js` gives a reusable Assigned→Accepted→InProgress→PendingVerification→Closed/Cancelled lifecycle with an approval gate; `execution-engine.js` gives a reusable Accept→Arrival(GPS)→Report execution runtime built on top of `process-engine.js`. Together these are a strong starting point for Daii's Picking/Packing/Dispatch tasks (§24) and Delivery execution (§28) — assign a task, accept it, execute it, record evidence/GPS, close it. Risk: both are currently wired only to Planning Center/Site-Visit-Task-specific repositories; the lifecycle logic itself is genuinely entity-agnostic and low-risk to lift.

**4. `kernel/sync-engine.js` + `kernel/sync-entity-registry.js` — Offline Sync Infrastructure (Classification B).**
A real, non-trivial offline-sync engine: idempotent push via `syncId`, optimistic-concurrency version-conflict detection, a registry pattern so the sync engine itself has zero entity-specific logic, and incremental pull with deterministic pagination/sorting. This directly serves blueprint §12 (Sales Rep Mobile App must work with server-side enforcement, implicitly needs to tolerate spotty connectivity for field sales). Risk: moderate — it is well-designed but non-trivial to port; only adopt if/when Daii commits to true offline-first mobile, otherwise defer to a later phase.

**5. `kernel/notification.js` — Multi-channel Notification Engine (Classification B).**
Working email/WhatsApp/SMS dispatch with templating, duplicate-suppression, and a delivery log, already used by 5+ modules in production. Reusable for Daii's Order/Deposit/Shipment status notifications (§32 Business Events). Must be hardened before reuse: credential fields are masked only in specific GET responses (manual per-endpoint masking, not centralized), and the WhatsApp/SMS adapters have zero retry/backoff — acceptable for a first cut, not for production shipment-tracking volume.

**6. `engines/organization-engine.js` — Company/Branch/Department/Team/Warehouse hierarchy (Classification B).**
Directly matches Daii's Foundation organizational model. Enforces a hard "single company" rule (`ENG-026`) that must be relaxed or removed for Daii (not necessarily wrong for V1, but should be a conscious decision, not inherited silently). Reads/writes are clean, validated, audit-logged — good bones to harden rather than rebuild.

**7. `engines/numbering-engine.js` — Document Numbering (Classification B, harden required).**
Small and generic (prefix + optional year + zero-padded sequence, never reuses a number). **However**, the Technical Debt Register documents a confirmed production defect (TD-29): the counter has no cross-check against the entity data it names, and restoring an older backup caused silent ID reassignment/collision on Asset, Sales Order, Purchase Request, Demo Request, Service Request, and Site Visit Task IDs. Any Daii port must add that cross-check (or move numbering into the same DB transaction as entity creation) before reuse — do not port the counter mechanism verbatim.

**8. `engines/purchase-engine.js` + `engines/sales-order-engine.js` — Approval-gated Order State Machines (Classification C).**
Not directly reusable as code (hospitality/warranty-specific fields and transitions throughout), but structurally these are the closest real analogs to Daii's Sales Order: a status transition matrix, manager-scope-aware permission computation (`computePermissions(record, user)` returning per-action booleans), full edit-history capture, and totals recalculated server-side on every write (never trusts client-submitted totals). Extraction risk: **high if copied wholesale** (the source-type taxonomy, warranty tie-in, and PR-backlink are all XNEXUS-specific) — treat this purely as a design reference for Daii's own Sales Order engine, built fresh against `process-engine.js` for the approval stages.

**9. `repositories/base-repository.js` + Repository Contract (Classification C).**
The *contract* (`getById/getByUuid/list/create/update/delete/restore/exists/find/count/transaction/lock/unlock`) is a clean, minimal repository interface worth keeping as an abstraction boundary. The *implementation* (one JSON file per entity, whole-file load/mutate/atomic-rename-persist) will not scale to Daii's multi-warehouse, concurrent-write, B2B order volume and must be re-implemented against a real database — extract the interface shape only, discard the JSON-file backing.

**10. `engines/feature-registry-engine.js` + `engines/navigation-engine.js` — Feature-flag-gated Navigation (Classification B).**
A clean two-engine pair: a role→feature-key registry, and a nav-tree renderer that defers 100% of its visibility logic to that registry (zero permission logic of its own). Good Foundation building block for Daii's Arabic/English, role-scoped admin navigation — low coupling, small surface, easy to harden.

## 5. Security / permission-model observations (Blueprint §33)

1. **No centralized RBAC/permission engine exists.** Every single Engine implements its own hardcoded `ROLE_ARRAY.indexOf(user.roleId) === -1` check (`SO_VIEW_ROLES`, `PR_MANAGE_ROLES`, `ORG_MANAGE_ROLES`, `TASK_ACCESS_ROLES`, `WAREHOUSE_MANAGE_ROLES`, `FGW_MANAGE_ROLES`, `QC_MANAGE_ROLES`, `ASM_MANAGE_ROLES`, ...) and file headers explicitly document this as a *deliberate, repeated architectural choice* ("duplicated, not shared — matches the established convention"). `roles-engine.js`'s own header even notes `permissions.json` exists but is unused — a "designed-but-unbuilt RBAC expansion." For Daii, which the blueprint explicitly requires to have Role/Permission/Scope/Limit as first-class Foundation engines (§7), this pattern must **not** be carried forward — it is the single biggest structural gap relative to Daii's stated security architecture.
2. **Auth is consistently enforced server-side at the route layer** (every `app.METHOD` call site in `server.js` and endpoint files pairs `requireAuth` with a `canX`/`checkPermission` gate) — this part of the discipline is good and worth preserving as a convention: no route was found relying on client-side/UI-only enforcement.
3. **`requireAuth` has real, tested hardening**: rejects revoked (logged-out) tokens, disabled accounts, and tokens issued before a password change (`passwordChangedAt >= iat`) — all fail-open only on a *read failure* (documented, deliberate, bounded risk), never fail-open on a positive "disabled" or "revoked" signal. This is a reasonable pattern to reuse for Daii's own auth middleware.
4. **`optionalAuth` intentionally skips revocation/disabled/stale-password checks** by contract (must never reject), and a separate `_xnEnforceTokenIntegrity()` helper exists for routes that need optional-token parsing *and* full enforcement — a two-tier pattern worth keeping, but easy to misuse if a future route reaches for the wrong one; Daii should make this distinction very explicit in its own Foundation.
5. **Numbering integrity gap (TD-29, confirmed production defect):** `NumberingEngine` trusts its own persisted counter with no cross-check against real entity data, causing silent ID reassignment after restoring an older backup — a correctness bug with security-adjacent consequences (ID collision across Sales Orders/Assets/etc.). Daii's numbering must be transactionally tied to entity creation (e.g., DB sequence or unique-constraint-enforced insert), not a free-standing counter file.
6. **No cross-file transactional guarantee**: `AssetEngine`'s own documented technical debt (`ASSET-MULTI-WRITE`) notes multi-file writes (movement→asset→reservation) have no explicit transaction — acceptable at XNEXUS's JSON-file scale, but exactly the class of bug Daii's Inventory Ledger + Reservation + Order Release chain (blueprint §17-20) must not inherit; this reinforces the case for a real ACID database from day one.
7. **Hardcoded default secret**: `kernel/website-integration-client.js` falls back to a literal string default (`'dev-only-integration-secret-do-not-use-in-production'`) when `XNEXUS_INTEGRATION_SECRET` is unset. Not itself a Daii capability, but a pattern to explicitly forbid in Daii's own config/secrets handling (fail closed / refuse to start, rather than fall back to a known dev value).
8. **A real credential-handling incident occurred during this project's own development** (`engineering/INDEX.md`, "Credential Incident — Root Cause Analysis," 2026-07-21): a live-testing script overwrote `passwordHash` for baseline admin accounts; root-caused and remediated with a permanent policy (never test against real/baseline accounts). Not a Daii-code finding, but worth carrying the *policy* forward (dedicated, tagged test accounts, never baseline/admin accounts, for any Daii QA/test automation).
9. **Credential masking in API responses is done ad hoc, per field, per endpoint** (e.g., `notification.js`'s `GET /api/notifications/config` manually masks `email.pass`, `whatsapp.apiKey`, `sms.authToken`, `push.serviceAccountKey` — with two of those four added only after a later security-review pass found the gap). Daii's Foundation should centralize secret-masking (e.g., a schema-level "sensitive field" marker) rather than repeat this per-endpoint manual pattern.
